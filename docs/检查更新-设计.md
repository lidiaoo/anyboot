# 检查更新 · 下载安装覆盖 —— 设计定稿

> 目标：应用内自动拉取 GitHub 最新 release，检查 → 下载 → 校验 → 覆盖安装 → 重启，
> 全程不打断用户当前任务，失败绝不弄坏现有安装。
>
> 本文档是设计定稿，落地时逐节实现；改动口径以本文为准。

---

## 0. 总体决策（先定大方向）

### D1：自研更新模块，不用 tauri-plugin-updater

| | tauri-plugin-updater | 自研 update.rs |
|---|---|---|
| 签名要求 | 必须 minisign 密钥对 + 发布 `.sig` | 自选（用 SHA-256 + release 域名白名单） |
| macOS 产物 | 需要 `.app.tar.gz`（现在只产 dmg，工作流要加） | dmg 直接用 |
| Linux | 只支持 AppImage | deb / rpm / AppImage 都能做 |
| Android APK / iOS | 不支持 | APK 能做；iOS 做引导 |
| 进度 UI | 插件自带事件，样式不可控 | 复用现有 `download_to_tmp_observed`，进度接自有 UI |
| 新增依赖 | 两个插件（updater + process） | 0（sha2/ureq 都在依赖树里） |

核心理由：**项目已经把难的部分做完了**——流式下载带节流进度（`hub_gateway.rs download_to_tmp_observed`，120ms 节流 + 末块必发）、GitHub 双镜像回退（`MIRROR_PREFIXES`：ghfast.top / gh-proxy.com）、sha2 依赖、阻塞线程模型（IQ6 定稿不引 async）。而官方插件覆盖不了 deb/rpm/APK，等于"官方插件 + 手写 deb/rpm/APK"两套并行，比一套自研更复杂。

### D2：数据源 = 双通道检查，资产按平台矩阵

**检查版本用"302 重定向探测"为主通道（2026-10-31 审计后定稿）：**

```
HEAD https://github.com/lidiaoo/anyboot/releases/latest
  → 302 Location: https://github.com/lidiaoo/anyboot/releases/tag/v0.2.0
  → 从 Location 解析 tag
```

- 零速率限制、匿名可用、不需要 API（实测 2026-10-31 直接拿到 `v0.2.0`）。
- 为什么不用 API 做主通道：匿名 API 限 60 次/小时/**每个出口 IP 共享**——实测当时本机出口 IP（66.90.98.35，代理/VPN 出口）配额已被陌生人耗光返回 403。共享 NAT / 代理用户这是常态，靠"间隔 ≥6h"保不住。
- API（`releases/latest`）**只作为补充通道**取更新日志 `body` / `published_at` / 资产元数据；403 时静默降级为"无日志只有版本号"，不报错。
- 资产下载走 `github.com/.../releases/download/...`，无 API 限速，镜像回退见 §3。

版本号到手后的资产清单不依赖 API：按 §2 矩阵的命名规则直接拼下载 URL（tag 已知）。这也意味着 **release 资产命名纪律（§6）是硬前提**。

### D3：版本比较 = 严格只升不降

- `tag_name`（如 `v0.2.1`）与本机 `app.package_info().version` 比较；解析失败按"无更新"处理并记录日志，**解析不出就当没有，不猜**（与 GRUB 零回落同一哲学：宁可不显示，不显示错的）。
- 相同版本不提示更新（哪怕资产更新过——要重发就改版本号，这是 release 纪律）。
- 回滚（降级）不在自动流程里，只提供"打开 Releases 页"手动下载入口。

## 1. 状态机（唯一权威）

```
idle ──check──▶ checking ──┬─▶ up_to_date（含"已是最新"原因）
                           ├─▶ error(可重试)
                           └─▶ available ──download──▶ downloading
                                              (progress 0-100)
                                          ┌──────────┴──────────┐
                                     verifying               error
                                          │校验通过
                                          ▼
                                    ready_to_install ──install──▶ installing
                                                                      │
                                                              应用退出/交接安装器
                                                                      ▼
                                                                   updated(重启后首启提示)
```

规则：

- 单飞：任何时刻只能有一个进行中的更新任务（下载中不允许重复点、不允许再发起检查）。
- **安全闸（install 前置条件）**：没有进行中的引导切换 / 电源操作 / 备份 / SFTP 传输；托盘与主窗全部按钮空闲。不满足则 install 按钮置灰并说明原因。
- 每一步失败都停在当前状态给出原因，**绝不自动跳过校验、绝不半装**。

### 状态结构（前后端同一份 JSON）

```rust
#[derive(Clone, serde::Serialize)]
pub(crate) struct UpdateState {
    pub phase: String,          // idle/checking/up_to_date/available/downloading/verifying/ready_to_install/installing/error/updated
    pub current_version: String,
    pub latest_version: String, // 空表示未知
    pub notes: String,          // release body 纯文本展示
    pub published_at: String,
    pub asset_name: String,
    pub downloaded: u64,
    pub total: u64,
    pub error: String,          // 非空即错误态
    pub checked_at: String,     // 最近一次成功检查时间
}
```

### Tauri 命令与事件

| 命令 | 行为 |
|---|---|
| `update_check()` | 拉最新 release → 版本比较 → 进入 available / up_to_date |
| `update_download()` | 按平台选资产 → 镜像回退下载 → SHA-256 校验 → ready_to_install |
| `update_install()` | 过安全闸 → 按平台安装策略执行（见 §4） |
| `update_dismiss()` | 记住"跳过此版本"（写 `update_skip_version`） |
| `update_state()` | 读当前状态（前端刷新/启动恢复用） |

事件 `update://state`：状态每次变化全量推送（与 hub_gateway 的 emit_state 同一做法）。

### 设置字段（加进 `state.rs Settings`，`serde_default` 缺省）

| 字段 | 默认 | 说明 |
|---|---|---|
| `update_auto_check` | `true` | 启动后 30s 静默检查一次 + 每 12h 一次；关掉只保留手动 |
| `update_skip_version` | `""` | 忽略此版本（用户点了"跳过这个版本"） |
| `update_mirror` | `"auto"` | `auto`（直连→镜像回退） / `direct` / 镜像名 |

## 2. 检查更新流程（详定义）

1. **主通道（零限速）**：`HEAD https://github.com/lidiaoo/anyboot/releases/latest`，从 302 的 `Location` 解析 tag（见 D2）。失败再试一次镜像前缀改写（`MIRROR_PREFIXES` 同样适用 `/lidiaoo/anyboot/releases/latest` 路径）。
2. **补充通道（可失败）**：匿名 `GET api.github.com/.../releases/latest` 带 `User-Agent: AnyBoot/<ver>`，拿更新日志 `body` / `published_at`；403/超时静默降级，notes 留空、UI 显示"暂无更新日志"。
3. 版本比较（D3）→ `available` / `up_to_date`。
4. 资产选择矩阵（**每个平台一条硬规则，找不到就报"本平台暂无安装包"，不跨平台拿**）：

| 平台 | 资产优先级 | 说明 |
|---|---|---|
| macOS (aarch64/x86_64 → universal) | `*.dmg` | 工作流产 universal 合包，一个资产全覆盖 |
| Windows x86_64 | `*setup*.exe` → 否则 `*.msi` | **优先 NSIS**：安装钩子（service-fragment、提权、防火墙规则）都在 setup 里，msi 没有这些逻辑 |
| Linux x86_64 | AppImage（若当前就是 AppImage 运行）→ `*.deb` → `*.rpm` | 按"当前怎么装的就怎么更"：`APPIMAGE` 环境变量在 → AppImage；否则查 dpkg/rpm 数据库 |
| Android（手机端 App） | `AnyBoot_*_debug.apk` | 手机客户端单独实现（见 §5） |
| iOS | 无自动更新 | 显示"请到 GitHub Releases 重新安装"+ 复制链接按钮 |

4. 版本比较已在第 3 步完成；矩阵选出的资产名按 tag 拼下载 URL：`https://github.com/lidiaoo/anyboot/releases/download/<tag>/<asset>`。
5. `update_skip_version` 命中 → 显示"有新版本 v0.2.1，你选择过跳过"，不弹提醒，仅设置页可见。

## 3. 下载与校验

- **复用** `download_to_tmp_observed`（ ureq 阻塞 + 256KB 缓冲 + 120ms 节流进度）到临时文件 `<asset>.downloading`，完成后 rename 成正式名。
- **镜像回退**（与 cloudflared/Tailscale 同策略）：GitHub 直连 → `ghfast.top/` → `gh-proxy.com/`，逐源尝试，每个源记录失败原因，全失败才报错。
- **SHA-256 校验（新增，必须做）**：GitHub 不提供资产哈希，工作流 release 阶段要追加一个 `SHA256SUMS.txt` 资产（`sha256sum` 所有产物）；客户端先拉这个小文件，校验主资产哈希一致才进 `ready_to_install`。哈希不符 = 下载损坏或被篡改，删除临时文件、报错、**不安装**。
- 只允许三种下载域名：`github.com`、`objects.githubusercontent.com`、`api.github.com` 及镜像前缀改写后的同路径 URL。镜像只改 host，不改路径（防止被诱导下到别的文件）。
- 断点续传不做：dmg/setup 最大 20MB 量级，失败重下成本低；做了反而引入半截文件状态。

## 4. 覆盖安装（按平台策略）

**总原则：下载、校验完成才动现有安装；安装动作要么成功要么原样不动，不出现"半新半旧"。**

### 4.1 macOS

1. 校验通过后弹确认：「将退出 AnyBoot 并安装 vX.Y.Z」。
2. 目标目录**不硬编码 `/Applications`**：从 `std::env::current_exe()` 反推所在 `.app` 与其父目录（用户可能装在 `~/Applications` 或自定义位置），安装回原位置。
3. 挂载 dmg：`hdiutil attach -nobrowse -readonly <dmg>`。
4. 用一个**独立的临时 shell 脚本**（detached 进程，`bash -c`）执行：`ditto` 复制 `.app` 到目标目录旁路临时名 → `hdiutil detach` → 原子 `mv` 覆盖旧 `.app` → `open` 新 `.app`。
5. 老进程 `std::process::exit(0)`。
- 为什么可行：macOS 允许替换运行中程序的 bundle（进程持有 inode）；ad-hoc 签名（`signingIdentity: "-"`）整包替换后签名随包走，无签名校验问题。
- 失败保护：先复制到临时名、成功才 `mv`，失败时旧 `.app` 未被触碰；临时目录在启动时清理。

### 4.2 Windows

**顺序是硬要求：先退出自身，退出前把安装器 spawn 成 detached 进程。反过来（先起安装器再退出）有竞态——NSIS 升级会先跑旧版卸载器（`PREUNINSTALL` 里 `ExecWait anyboot.exe --uninstall-service`），运行中的本体不退出，卸载器删文件就会失败。**

1. 校验通过后弹确认。
2. 本体优雅退出前的收尾顺序：**保存所有持久化状态**（`Settings` 落盘、窗口几何、托盘位置）→ 停 watcher 线程、断开 helper 服务连接 → **安全闸确认无进行中的引导/电源操作** → spawn detached `setup.exe /S` → 本体 `exit(0)`。
3. `setup.exe /S`（NSIS 静默）：perMachine 模式自带 UAC 提权；升级路径 = 旧版卸载器（停删服务）→ 装新文件 → `POSTINSTALL` 重新注册服务（现有 `installer-hooks.nsh` 已按此设计，钩子里只有 `ExecWait` 无 UI 交互，`/S` 下安全——2026-10-31 审计确认）。
4. 新版安装完成后由 hook 启动新版：`.onInstSuccess` 补 `Exec '"$INSTDIR\anyboot.exe"'`（**可执行名是小写 `anyboot.exe`**，与钩子里现有一致；`/S` 下无完成页，只能靠 hook 或用户手动启动）。
- Tauri NSIS 模板在静默模式下对"运行中实例"的处理（是否 taskkill 强杀）无法本地证实（bundler 模板在 CI 侧）——**设计不依赖该行为**，"先退出"把它整个消掉。

### 4.3 Linux

| 当前安装形态 | 安装动作 |
|---|---|
| AppImage | `APPIMAGE` env 指向自身 → 下载到 `X.tmp` → `chmod +x` → 保留旧文件为 `.old` → `mv` 原子替换 → `exec` 自身（同 fd，无缝重启） |
| deb | 走 `linux_priv` 提权通道：`pkexec dpkg -i <tmp>` → 成功后重启应用 |
| rpm | 同上：`pkexec rpm -Uvh --replacepkgs <tmp>` |

- AppImage 的 `.old` 回退：启动时若主文件无法执行（校验签名段失败）且存在 `.old`，提示用户可还原。
- deb/rpm 更新**不改配置**：AnyBoot 的配置在 `~/.config`，包管理升级不动用户目录，天然安全。

### 4.4 Android（手机端 AnyBoot Remote 客户端）

1. 设置页加「检查更新」：请求同一 `releases/latest`，选 `AnyBoot_*_debug.apk`。
2. 下载到 app 私有目录 → `FileProvider` + `ACTION_INSTALL_PACKAGE` intent → 系统安装器接管。
3. 需要 `REQUEST_INSTALL_PACKAGES` 权限声明；用户首次会看到"允许安装未知应用"系统弹窗——文案里提前解释。
4. 客户端不做覆盖逻辑，全部交给系统安装器（系统自己处理"同包名覆盖升级"，数据保留）。

### 4.5 iOS

不做自动更新（未上架 TestFlight/AppStore 前 ipa 无法自装）。UI 提供「复制下载链接」+ 跳转 Releases 页。

## 6. 工作流配套改动（build-all.yml）

> **2026-10-31 审计更正：现在的工作流只有 5 个 build job（产物只 upload-artifact），没有任何 release 发布步骤**——v0.2.0 的 release 是手动 `gh release upload` 建的。所以配套改动不是"追加校验文件"一个动作，而是先建 release 发布 job：

1. **新增 release 发布 job**（依赖全部 5 个 build job 成功）：`gh run download` 收齐 8 个产物 → APK 重命名 `AnyBoot_<version>_debug.apk` → 生成 SHA256SUMS → `gh release create/upload`（`--clobber` 支持同 tag 重发）：

```yaml
release:
  needs: [desktop-windows, desktop-linux, desktop-macos, android, ios]
  runs-on: ubuntu-latest
  steps:
    - uses: actions/download-artifact@v4
    - name: 整理命名 + SHA256SUMS
      run: |
        mkdir rel && cd rel
        # ... 逐产物 mv 成 AnyBoot_<version>_<platform>.<ext> ...
        sha256sum *.dmg *setup*.exe *.msi *.deb *.rpm *.AppImage *.apk *.ipa > SHA256SUMS.txt
    - run: gh release create "v${{ inputs.version }}" rel/* --generate-notes
      env: { GH_TOKEN: "${{ secrets.GITHUB_TOKEN }}" }
```

2. 资产命名纪律：`AnyBoot_<version>_<platform>.<ext>`（现有 `AnyBoot_0.2.0_debug.apk` 已符合；**iOS 的 `AnyBoot-unsigned.ipa` 没带版本号，发布 job 里统一重命名**）；**改名的版本，更新矩阵（§2 表）同步改**。
3. 建议加 `on: push: tags: ['v*']` 触发路径，配合手动 `workflow_dispatch`；客户端只认 latest release，tag 与 release 一一对应。
4. release body 是更新日志的数据源——写清楚人类可读的变更点，客户端原样展示（纯文本渲染，不执行 HTML）。
5. 客户端只信 `releases/download/<tag>/<固定资产名>`，**release job 必须保证资产名与版本号一致**（tag v0.2.1 里放 `AnyBoot_0.2.0_...` 就永远下载比对失败——SHA256SUMS 会兜住，但用户看到的是报错）。

## 7. 补充考虑（容易被漏的点）

1. **更新日志安全**：release body 只按纯文本 / 换行渲染，绝不 innerHTML 注入 webview。
2. **GitHub 限速退避**：主通道 302 探测无限速；补充通道 API 返回 403/429 时**静默降级**（无日志照常可用），不显示"检查太频繁"——那是 API 的事，检查本身没失败。
3. **代理友好（2026-10-31 审计更正）**：ureq **不是**默认读 `https_proxy`——环境代理只在 `proxy-from-env` feature 下生效（ureq 2.12.1 `agent.rs` 实证：`try_proxy_from_env` 由该 feature 门控），而本项目是 `default-features = false, features = ["tls"]`。**落地时给 ureq 加 `proxy-from-env` feature**，否则走系统代理的用户更新检查/下载全断。设置里不加代理配置（用户系统级代理已覆盖）。
4. **检查时机避开首启动关键路径**：启动后延迟 30s 再查，不跟引导列表扫描抢 HTTP/线程。
5. **多显示器/多窗口无关**：更新状态走全局事件，托盘/设置页/主窗三处消费同一份 `update://state`，不做各查各的。
6. **磁盘空间预检**：下载前查临时目录剩余空间 ≥ 资产大小 × 2（下载 + 解压余量），不足直接报「磁盘空间不足」。
7. **版本号写入二进制一致性**：`tauri.conf.json` 与 `Cargo.toml` 版本必须同步（现在都是 0.2.0）；发布流程里加一步"两处一致"检查，否则自比较永远相等。**Android 端同理**：`versionName` 要与 tag 口径一致（`0.2.1` 对 `v0.2.1`，手机端比较时剥 `v` 前缀），否则手机永远提示"已是最新"或永远提示更新。
8. **Windows 安装器静默模式兼容自定义钩子**：✅ 已审计（2026-10-31）——现有钩子只有 POSTINSTALL/PREUNINSTALL 两个 `ExecWait`，无 UI 交互，`/S` 下安全；不需要逐 hook 再查，但**以后往 installer-hooks.nsh 加 UI 交互时必须考虑静默模式**。
9. **Android debug 包升级签名一致**：debug 签名覆盖安装 OK；若未来出 release 签名版本，跨签名不能覆盖升级，需先卸载——文档注明数据会丢。
10. **隐私**：检查更新不携带任何本机信息（无 OS 版本、无 UUID 上报），GitHub 只看到一次匿名请求。
11. **失败可见性**：所有失败都落 `trace` 日志（`trace.rs`），错误文案同时给"下一步该做什么"（沿用 GRUB error 口径的经验：不说"失败"，说"失败了 + 为什么 + 你能做什么"）。
12. **首次检查失败不打扰**：自动检查失败静默（托盘不弹错），只有手动检查才把错误显示出来——自动通道坏了不该变成每日骚扰。

实现时相对设计的偏差（均已在代码注释里说明）：

1. **ureq 没开 `json` feature**：API 响应手动 `into_string` + `serde_json::from_str`，不新增 feature。
2. **`install_worker` 里不能 `thread::sleep`**：项目有 `blocking_guard` 守卫（同步命令调用链禁止阻塞 token）。安装交接后直接 `app.exit(0)`——macOS 脚本自带 1s 等待、Windows 安装器自己处理运行中实例、Linux 已 spawn 新进程；命令体只起线程，按守卫规范加了 `// blocking-ok` 显式豁免说明。
3. **macOS 安装脚本落点改到临时目录**：`/Applications` 是 `root:admin 775`，普通用户写不进去；脚本与挂载点都放 `temp_dir()/anyboot-update`，目标 `.app` 路径仍由 `current_exe` 反推。
4. **前端只在 Tauri 本机窗口显示**：`IS_BROWSER` 下整块移除（远程页面没有 `update-state` 事件通道，也不该允许远程触发本机安装）。
5. **`update_check` 改 async 命令 + `spawn_blocking`**：同步命令跑在 WebView 的 IPC 线程上，而检查含两个网络请求（连接 10s / 读 20s 超时）——网络被黑洞时会整窗卡死（`blocking_guard` 只认固定阻塞 token，认不出 ureq，得靠人判）。托盘入口改调同步内部的 `check_with_busy`。

## 9. 明确不做（Negative Scope）

- ❌ 增量更新 / 差分下载（bsdiff 等）——体积小，不值得复杂度。
- ❌ 多通道（beta/nightly）——只有一个 latest release，以后有需要再加。
- ❌ 强制更新——永远允许"跳过此版本"。
- ❌ 自动静默安装（下载完自动重启覆盖）——安装动作必须用户点一次确认；"下载完自动装"是拿用户正在做的引导/电源操作冒险。
- ❌ 内置 GitHub token——检查与下载都有匿名通道（302 探测 + release 下载），token 入码库是安全事故。
