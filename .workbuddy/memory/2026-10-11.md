## 第九轮：主界面加长 + GRUB 列表三种展示方式

经确认：高度加到 **900**；展示方式**两种都做、可切换**（内嵌 / 加宽主窗口 / 独立跟随窗口）。

### 实现

1. **高度 680 → 900**：`tauri.conf.json`，常量 `MAIN_HEIGHT = 900` 与之对齐。

2. **`Settings.grub_list_view: String`**（inline / wide / window，serde default）+
   `normalize_grub_list_view()` 纯函数（不认识的值回落 inline，有单测）。
   经 `SettingsView` 的 `#[serde(flatten)]` 自动带到前端（`settings.grubListView`）。

3. **窗口形态（全部后端负责）**：
   - `apply_grub_list_view(app, mode)`：
     - inline → 主窗口 460×900 + 关闭独立窗口；
     - wide → 主窗口 **920**×900 + 关闭独立窗口；
     - window → 主窗口 460×900 + 开/显示独立窗口。
   - `open_grub_list_window()`：创建 `grub-list` 标签的窗口（440×860、resizable、
     `visible(false)` **先建后摆**——沿用通知窗口「先在默认位置画一帧白底」的教训），
     仅当主窗口可见时才开（托盘态不蹦出来）。
   - `place_grub_list_window()`：吸附到主窗口旁——首选右侧，放不下换左侧，
     再不行贴工作区右缘；纵向对齐主窗口顶边并夹进工作区。全程物理像素。
   - **跟随**：`on_window_event` 里监听主窗口 `Moved` → 重摆独立窗口；
     主窗口 `CloseRequested`（藏托盘）→ 独立窗口跟着藏；`show_main_window()` → 补开。
   - **用户点独立窗口标题栏 ×**：`prevent_close` + 隐藏 + **设置退回 inline** +
     publish_ui（下拉框跟实际状态一致，不销毁窗口，重开便宜）。
   - 启动时（setup 尾部）应用已保存的模式：wide 加宽；window 且非 start_in_tray 才开窗。

   - GRUB 区顶部加「列表展示」下拉（#grub-view-mode）；window 模式下内嵌列表隐藏、
     显示一行说明（#grub-window-note），下拉值只在和快照不一致时才写（防打断用户）。
   - `ui/grublist.html/js/css`（新）：独立窗口页面。数据同源——进场
     `invoke("get_ui_state")`，之后监听同一个 `ui-state-changed` 广播（`app.emit`

   - `styles.css`：`@media (min-width: 700px)` 时 `.grub-list` 铺**两列**、高度放开

## 第九轮补丁：三种展示方式来回切换会失效

用户原话：
> 这三种来回切换会有bug导致切换失效

**根因（事件乱序覆盖）**：`apply_grub_list_view` 切走 window 模式时用的是
`close_grub_list_window()`（`window.close()`）。但 `CloseRequested` 处理器是给
「用户点标题栏 ×」设计的——里面会**把设置强制改回 inline 并 publish_ui**。
Tauri 的关闭流程异步走主线程，这个改写比切换命令自己的 `publish_ui` 晚到：
设置刚存成 wide/window 就被改回 inline 并广播，前端下拉框弹回去、内嵌列表又显示
出来，而主窗口尺寸还是宽的（或独立窗口已开）——来回切几次状态就永久错乱。

**修法**：模式切换一律**只 `hide()` 不 `close()`**（`apply_grub_list_view` 里
`close_grub_list_window` 全部换成 `hide_grub_list_window`，该函数已删除）。
`CloseRequested` 路径现在只剩用户点 ×，语义干净。附带好处：窗口常驻不销毁，
反复切换不用重建 webview。

**验证**：`cargo test --release` 68 passed / 0 failed / 0 warning；
`cargo build --release` 成功（11467264 字节，08:32）；`anyboot.exe.pending-9d1`
残留已清（用户退出了旧实例）。教训：**「程序化关窗」绝不能复用「用户关窗」的
CloseRequested 语义**，要么 hide 要么加标志位区分。

  无标题栏 = 没有最小化/关闭按钮、也没有拖动着力点。Alt+F4 仍会被

- grublist.css 给 body 加描边（无边框窗口自己衬成面板）。

### 2. 主窗口贴边自动隐藏
- `Settings.main_auto_hide: bool`（默认关）+ 设置区复选框（#main-auto-hide）+
  `set_main_auto_hide` 命令。开 = 启动守护线程；关 = 立即展开。
- **实现方式**：这个 Tauri 版本的 `WindowEvent` **没有** CursorEntered/CursorLeft
  （编译报 E0599 实锤），改用守护线程每 120ms 轮询 `AppHandle::cursor_position()`：
  - 未停靠 + 光标离窗超 350ms → `dock_main_window`（按 `nearest_edge` 贴最近边，
    露 6px 条）；
  - 已停靠 + 光标压到露出的条上 → `undock_main_window`（推回工作区边缘）。
- 线程用 `static WATCHER_RUNNING: AtomicBool` 防重复；开关关掉时自检退出；
  setup / show_main_window / 勾选时三处都会确保它在跑。
- 贴边状态存 AppState（docked / edge / dock_pos）；贴边时 GRUB 独立窗口跟着藏，
  展开时跟着回。
- 关键细节：dock 里**先写 AppState 再 set_position**——贴边触发的 Moved 靠
  dock_pos（24px 容差）认出是自己的回声，不做位置夹取；用户抓着边条拖跑则视为
  解除停靠，落回正常夹取。

### 3. 主窗口拖到任何地方都完整显示
- Moved 处理（handle_main_moved）里做位置夹取：在**相交面积最大的显示器**的
  工作区内 clamp（`clamp_to_work` 纯函数，跨屏拖动自动落到目标屏，不会拽回去）。
  贴边停靠的那次越界是唯一豁免。窗口大于工作区时钉左上角。

## 第十一轮：最小化后独立窗口丢失 + 选中项顶部横幅

用户原话：
> 我选择了独立窗口但是点了主菜单的最小化之后 再点开主菜单 发现独立窗口没了,,,这三种方式都要在最顶部显示选择的系统是哪个 如果是级联的 父级选择的名字+子级选择的名字 最后一级选择的都要大字而且颜色明显 他的上级小一点的字

### 1. 最小化后独立窗口丢失（根因 + 修法）
- Windows 最小化窗口时把它挪到屏幕外 **(−32000,−32000)** 并触发 Moved ——
  旧代码把这当普通移动处理：`clamp_main_window` 跟最小化打架，
  `place_grub_list_window` 又按这个坐标把独立窗口摆到工作区角落。
- 恢复路径上 `open_grub_list_window` 的 `main.is_visible()` 守卫可能读到
  `show()` 刚派发还没生效的**过期值**，直接 return，独立窗口没被补开。
- 修法（三层）：
  1. `is_minimized_position()`（x/y < −20000）识别最小化态：Moved 里只藏
     独立窗口、立即 return，不夹取不摆位。
  2. `open_grub_list_window(app, force_show: bool)`：托盘呼出 / 恢复 / 失焦回归
     都传 `true`，跳过 is_visible 过期值；只有 setup 托盘启动那次传 `false`。
  3. `Focused(true)` 事件（原来只处理 Focused(false)）也补开独立窗口 ——
     覆盖 alt-tab 恢复这条路径。

### 2. 选中项顶部横幅（三种展示方式共用）
- `grub-list-view.js` 新增 `renderGrubActive(container, grub)`：
  activeSelector（nextEntry ?? savedEntry）找到条目；有 submenu 就先渲染
  **父级名 ›**（11px 灰字），再渲染子级名（17px 加粗 `--link` 主题色）；
  顶层条目只有大字；没选过显示「尚未选择启动项」（未填 uuid 时整条隐藏）。
- 主窗口 `#grub-active`（grub-head 之下，**不受展示方式影响**，window 模式也显示）；
  独立窗口 `#grub-window-active`（header 之下）。两页共用同一渲染器与 CSS。

### 验证
- `cargo test --release` 68 passed / 0 failed / 0 warning；
  `node --check` 三个 JS 全过。
- 新 exe：11469312 字节，09:00。`anyboot.exe.pending-b3e` 被运行实例占用，
  等用户退出后删。

## 回合 18：贴边隐藏五项整改（10:44）

1. 深度绑定：watcher 每 tick 校验 —— mode=window 且主窗口可见时独立窗口

## R28.24 「同步 grub.cfg 到 ESP 失败: 权限不够 (os error 13)」根因 + 提权写入
- 实测（uid 1000 视角）：`open /boot/grub/grub.cfg` → EACCES（`grub-mkconfig` 自己

  （fstab 挂的 vfat 无 `uid=`，属主 root、dmask=0022）。报错发生在 `fs::copy` **开源源文件**
  那一步（Python shutil 复现：e.filename 就是源文件）。
- 设计缺口：`grub_collect` 假设 ESP 目录当前用户可写 —— 只有程序自己
  `mount -o rw,uid=<用户>` 挂的才成立；系统挂在 /boot/efi 时 `grub_locate` 直接复用
  现成挂载点（mount=None），没有任何提权路径。切换条目写 grubenv 同样会失败。
  顺带确认：`/etc/grub.d/09_anyboot` 与程序内置模板逐字一致 → pkexec install 在本机可用。

  `user_can`(access 2) / `same_size_and_time`(size+2s 容差) / `privileged_install`
  (`install -p -m 0644`，`mount_command` 自动套 pkexec) / `stage_and_install`（内存字节先
  落 0600 暂存文件）/ `write_esp_bytes` / `copy_into_esp`；
  `grub_collect`、`grub_write_env` 改走这两个入口。副本 size+mtime 一致就跳过，
  同一份 grub.cfg 不会重复弹授权框（普通路径用 `File::set_modified` 补 mtime）。
  远程不许弹框：`RemoteNoGuiAuth::enter(remote_allow_gui_auth)` + 模块级
  `REMOTE_NO_GUI_AUTH`，`privileged_install` 据此直接失败并给处置办法。
- README「权限说明」补写了两坎与两条免弹框办法（fstab 加 uid= / anyboot-grub-setup.sh）。
- 验证：`cargo test --release` 72 passed（新增 5 条）→ `cargo build --release`；

## 回合 27：收掉「贴边瞬间白条先闪在屏幕上方再跳过去」

- **先说一个判断错误**：我一度把 `_NET_FRAME_EXTENTS = 0,0,37,0` 当成「去装饰没生效」。
  放大截图看清楚了 —— 停靠态**没有标题栏**（底部那条按 `mainDockStripColor` 渲染的
  白条也在），去装饰是生效的；`_NET_FRAME_EXTENTS` 只是 WM 写的提示值，Muffin 在
  去装饰后**既不更新也不删除**，停在旧值。判据应该看应用请求的
  `_MOTIF_WM_HINTS.decorations`（放开 `GSETTINGS_BACKEND=memory` 时该属性直接不存在）。
- **细采样（60ms）测到的真实轨迹**（客户区几何，250ms 采样会正好跳过这段）：
  ```
  +180ms 570 100 460x900   ← 还没贴
  +240ms 570  63 460x40    ← 缩成条了，但停在**屏幕上方**（旧窗框原点）
  +600ms 570  63 460x40    ← 一直卡着
  +660ms 570 960 460x40    ← 481ms 后被「回钉」兜底挪到位
  ```
  日志同一时间线：`dock begin target=(570,960)` → `hold (570,26)` → **481ms 后**
  `snap back (570,26) -> (570,960)`。**结论：首次 `set_position` 根本没落地**，
  是回钉把它救到位的。
- **根因**：`dock_main_window` 在**可见窗口**上做
  `set_decorations(false)` → `set_size` → `set_position` 这套翻转。去装饰触发的
  重父化会吃掉同批发出的 position 请求，窗口于是停在「旧窗框原点 + 新尺寸」。
  代码里 `undock_main_window` 早就为同一个问题写了注释（「带着可见窗口做
  set_decorations → set_size → set_position，标题栏会先在细缝上长出来、再跳到
  最终位置」）并用了「隐藏态做完再 show」—— dock 方向漏了这半套。
- **修法（a）**：`set_size`/`set_position` 包进 `hide()` … `show()`（用
  `was_visible` 判断，别无条件 hide）。**monitor/target 必须在隐藏之前算完**：
  tao 在窗口不可见时 `current_monitor()` 会退化成主显示器，多显示器下会把边条
  吸到错的屏上。改后轨迹：`+240ms` 就是 `570 960 460x40`，中间态消失。
- **顺带修掉（b）坐标系混用**：watcher 停靠态的漂移判定拿 `outer_position()`（窗框）
  去比 `dock_pos`（客户区，`Moved` 载荷也是客户区）。加 `inner=({},{})` 到心跳后
  实测：带装饰 `outer=63 / inner=100`；**去装饰后 `outer=923 / inner=960`**，
  而 xwininfo 实测客户区正是 960 —— 说明去装饰后 GDK 那份 frame extents 缓存
  **不再刷新**，`outer_position()` 会持续偏一个标题栏（37px > 24 容差）→
  **每一拍都假漂移**，3 次回钉额度全被空转吃光，真出现位移反而没人修。
  修法：停靠态改用 `inner_position()`，并**复用 `docked_move_action`** 这个已有纯函数，
  让事件路径与轮询路径在同一个坐标系、同一个容差下判定。
- **验证**：`cargo test --release` 74 passed；复现台最终一轮 —— 中间态消失、
  `snap back` 一行不剩、三个场景判据（稳定/悬停展开/可重复）全 ✓。
- 复现台脚本已同步（加了 `motif()` 判据、把误导性标签改掉）。

## 回合 28：贴边隐藏两处「混坐标系」bug（Windows 看不见，只在 Linux 炸）

按回合 27 的收尾计划复跑 `ENTER=0` 验证 `AUTO_HIDE_SETTLE_MS` 启动宽限，结果**全绿**，
但顺手加的三条取证日志暴露出两个更深的、同源的问题。两条都有实测证据，都已修 + 单测钉住。

### 取证：给「谁动了窗口」加日志（`ANYBOOT_AUTOHIDE_DIAG=1`）
- `moved diag: event=(x,y) outer=(x,y) inner=(x,y)` —— **每一条** Moved 都打；
- `clamp: (x,y) WxH -> (x,y)` —— 只有真的夹取才打；
- `center main -> (x,y) outer_size=WxH` —— 居中落位。
判断法：**Moved 出现而前后没有任何应用侧落位行 = WM 动的**。

### 发现 1（顺带排除嫌疑）：启动后 4~5s 窗口自己往下跳 32px
`moved diag: event=(570,63) outer=(570,63) inner=(570,100)`，前面一条应用侧日志都没有
（居中/夹取/follow/dock/undock 全部有自己的行且都没出现），`Cargo.toml` 里也没有
window-state 插件 → **是 Muffin 在窗口首次被查询/指针进入后约 0.5s 按自己的记录重摆**。
y 从 31 → 63（窗框底边贴工作区底），x 保留我们的 570。幂等、无害（重摆后正好是
edge-flush，于是被贴边逻辑收走是**功能正常**，不是 bug）。**不是我们的代码，别再顺着
set_position 找。**

### 发现 2：停靠态判据拿窗框坐标比客户区落点 → 白条闪一下
`handle_main_moved` 的停靠分支：`docked_move_action(Moved载荷, dock_pos, 24)`。
但 tao 的 `Moved` 载荷 = `window.root_origin()` = **窗框**坐标，`dock_pos` 是
`set_position` 落点 = **客户区**，去装饰后恒定差 37px > 容差 24
→ 「容差内 = 自己的回声」这条**永远不成立**：停靠稳态下任何一条 Moved
（WM 重发 configure、点白条引发 raise…）都被判成「用户把白条拖走了」→ 展开，
160ms 后 watcher 又贴回 = **白条闪一下**。
证据（新加的 NUDGE 实验，横向挪 10px < 容差）：
```
1791713881454 moved diag: event=(580,923) outer=(580,923) inner=(580,960)
1791713881454 moved: docked but off dock_pos (580,923) vs (570,960) -> release
1791713881612 dock begin edge=Bottom from=(580,63) size=460x937 target=(580,960)   ← 160ms 后又贴回
```
修法：新增 `fn main_client_position(app) -> Option<(i32,i32)>`（就是 `inner_position()`），
停靠分支改读它；watcher 轮询路径原来内联的 `inner_position()` 也换成它 —— 两条路径
同一个来源、同一个纯函数、同一个容差。修后同一实验：`仍停靠（静默保持）✓`，
日志里 `event=(580,923) inner=(580,960)` 之后没有任何 release。

### 发现 3：`undock` 的反算按窗框、喂给客户区 API → 展开后整窗偏高一个标题栏
```rust
// 修前（按窗框算）
DockEdge::Bottom => (pos.x, work.bottom - outer_h + border_bottom)   // = 63
```
`set_position` 落的是**客户区** → 客户区落到 63（本该 100），靠 WM/后续纠正才回来。
证据：修前 `undock edge=Bottom restore=460x900 target=(570,63)` → 第一条 Moved
`event=(570,26) inner=(570,63)`，再补一条 `event=(570,63) inner=(570,100)`；
修后 `target=(570,100)` → **第一条就是** `inner=(570,100)`，没有 37px 偏移。
修法：抽出纯函数 `undock_target(edge, work_x/y/w/h, client_x, client_y, client_w, client_h)`
按客户区算（顶边 `client.y = work.y`、底边 `work.bottom - client_h`、左右同理，另一轴保持
客户区当前坐标），并新增单测 `undock_target_sticks_client_area_to_work_edge`（含副屏工作区
带偏移的用例）。连带把没人再需要的
`auto_hide_borders: Option<(top,bottom,left,right)>` 收敛成
`auto_hide_client_offset: Option<(left,top)>`（下/右偏移在客户区算式里用不上），
`undock` 里为此服务的外框换算（`outer_w`/`outer_h`、现场量四边）一并删掉。

### 坐标语义定稿（tao 0.35.3 源码 + 实测）
| API | 坐标系 |
| --- | --- |
| `set_position` / `set_size` | **客户区** |
| `inner_position()` / `inner_size()` | **客户区**（去装饰后仍准，唯一可信来源） |
| `outer_position()` / `outer_size()` | **窗框** |
| `WindowEvent::Moved` 的载荷 | **窗框**（= `root_origin()`，和 outer 同一个数） |
Windows 上 outer == inner（`SetWindowPos` 就是窗口矩形），所以同一份算式在那边恰好对 —— 
这就是「Windows 好了、Linux 不行」的机制。定则：**判位只用 `inner_position()`**。

### 发现 4（同一类，顺带收掉）：左/右侧贴边时「另一轴保持原位」也用错坐标系
`strip_geometry(edge, …, pos_x, pos_y, strip)` 的 `pos_x/pos_y` 传的是
`outer_position()`（**窗框**），而它返回的落点是**客户区** → 左/右侧贴边时
条子的 client y = 窗框 y（比原位高一个标题栏）；展开时又按客户区锚回 →
**每贴一次就漂一截**。（Bottom/Top 用得到的是 x，Muffin 的左边框=0 所以看不出来，
这也解释了为什么之前几轮没暴露。）
- 修法：调用点改用 `window_client_position(&main)` 的客户区坐标；形参改名
  `client_x/client_y`；`strip_geometry` 的既有单测补两例「工作区带偏移」（副屏/面板）。
- **改前/改后（同一复现台场景 `LEDGE=1`：挪到左缘再移开光标）**：
  - 改前：`贴边前客户区 y=87` → `贴左边: 0,50 40x900`（**偏 −37px** ✗），
    日志 `dock begin edge=Left from=(4,50) target=(0,50)`（target 是窗框值）。
  - 改后：`dock begin edge=Left from=(4,50) target=(0,87)` → 条子 `0,87 40x900` ✓
    与贴边前客户区 y 一致。

## 回合 29：把「呼出保护」从「无法验证」变成「可自动化」（诊断钩子 + RECALL 场景）

回合 28 收尾时留了一条「托盘呼出这条路本机没有托盘宿主、无法自动化」的坦白。
本轮把它补上：给产品加了一个**只在环境变量下生效**的诊断钩子，用复现台跑通了整条链路。

### 产品侧改动（一个钩子，两行调用）
```rust
/// ANYBOOT_AUTOHIDE_DIAG=1 且 ANYBOOT_AUTOHIDE_DIAG_RECALL_MS=<ms> 时，
/// 启动 N 毫秒后模拟一次「托盘呼出」（走同一条 ShowOrigin::Recall）。
fn spawn_diag_recall(app: &AppHandle) { /* 不设变量直接 return */ }
```
- 调用的就是**现有**入口 `show_main_window(&app, ShowOrigin::Recall)`，不复制逻辑；
  在 `setup` 末尾调用一次。不设这两个环境变量时行为与改动前**完全一致**。
- 为什么值得留在代码里：呼出保护的失效形态是「呼出 → 立刻贴回 → 再呼出」的互闪死循环，
  是用户能看见的"linux 不行"典型症状，而它没有托盘宿主就零覆盖。

### 复现台新场景（`RECALL=1`，配合 `POS=free`）
`RECALL=1 POS=free bash run.sh <bin> <tag>`，三条断言 + 判据纪律：
1. 贴边成条 → 模拟呼出 → 窗口展开 ✓（实测 `undock edge=Top restore=460x900`）
2. **呼出后光标仍在窗外 4s 不许被贴回** ✓ —— 日志证据：连续三拍心跳
   `near_edge=true inside=false pending_enter=true outside_ticks=0`（
   没有这层保护，`near_edge=true` + 光标在外 240ms 内就会贴回，即互闪）
3. 光标进过窗口（心跳里 `undocked: left window … pending_enter=false`）再离开 →
   250ms 内重新贴边 ✓（`dock begin edge=Top from=(108,0)`）
- **`POS` 开关**：位置模式默认 `center`（与用户设置一致）；验证「呼出保护」必须用
  `POS=free` —— center 会把窗口居中挪离边，`near_edge=false` 时贴边逻辑本来就不该触发，
  压不到保护。脚本第三条断言在 center 下自动跳过并说明原因。
- **判据纪律（踩过）**：观察窗起点可能早于定时事件本身，所以统计口径是
  「首次展开之后有没有变回条子」，不是「窗口期内有没有出现过条子」——
  否则把「呼出前那一拍」算成贴回，报假 ✗。
- 另外 `RECALL=1` 时主窗口筛选门槛降到 1000：free 模式下 WM 一开始就把窗口摆在贴边处，
  启动 6s 后它已经是 460x40 的条子，按整窗面积（40000）筛会直接判「找不到主窗口」。

### 其他踩到的（都已写进脚本注释/skill）

## 回合 30：左/右缘拖动 → 主界面变长 + GRUB 窗乱闪乱跳（两个独立 bug）

用户原话：「现在从屏幕左边左右拖动 从屏幕右边左右拖动也一样 主界面会变长还会导致grub窗口乱闪乱跳」
前置条件：**GRUB 独立窗口模式**（`grubListView=window`）。现象有两个独立的成因，都修了。

### bug A：未映射窗口的 `outer_size()` = 0x0 → 对齐目标算出 900x1257
- 实测（`shots/drag-3`，改前）：
  ```
  grub 首同步: main_outer=0x0 list_inner=440x320 list_outer=0x0 vis=false
  align grub enter: vis=false inner=440x320 outer=0x0 margin=-440x-320 main_outer=460x937 target=900x1257
  ```
  `target = 主窗外框 − 边距`，边距 = `外框 − 内框` = `0 − 440` = **负数** →
  变成「主窗外框 **加** 内框」。900x1257 比 1600x1000 的屏幕还大，WM 钳住后
  这批 configure 回声又被当成「用户拉了边框」→ 反推主窗尺寸 = **主界面变长**。
- 修：新增纯函数 `grub_align_target(main_outer, list_inner, list_outer) -> Option<..>`，
  任一边为 0（= 还没收到过 configure，tao 的 `outer_size` 初值取的是**坐标**）
  或边距为负（尺寸错拍）→ `None`，不改尺寸；**位置照摆**（`return` 掉会把吸附一起吞了）。
  `open_grub_list_window` 的首同步块同样改用它（原来也吃这个 0x0）。
- 修：`main_size_from_grub(grub_outer, borders) -> Option<..>` 同样拒绝 0/负边距，
  `None` 时直接 `return`，宁可不动也不把主窗改成错的尺寸。

### bug B（更要命）：GRUB 的 Moved 回声被当成「用户拖 GRUB」→ 反拽主窗
- 实测（`shots/drag-fixed`，改到一半时）：
  ```
  1791720113087 place grub -> (664,13) main=(1136,13)
  1791720113088 follow main -> (192,13) grub=(664,13)      ← 1ms 后自己反拽自己
  ```
  192 = GRUB 左侧位置（`664 − 460 − 12`）：主窗被从 x=1136 一路拽到 192。
  一次「拖主窗」里 `follow main` 触发 **904 次**（改前 drag-2=833 / drag-3=1036）——
  两个窗口毫秒级互拽 = 用户看到的「GRUB 窗乱闪乱跳」；主窗被拽离边缘后
  `inside=true` 贴不回边 = 「主界面（不贴回来了，看着）变长」。
- 根因：`GRUB_FOLLOW_TARGET` 那种「**匹配一次就清成 u64::MAX**」的一次性哨兵。
  一次 `set_position` 在 X 上会产生**多条同坐标 Moved**（同坐标 1ms 内两条：
  configure 回声 + 重父化/raise）→ 第二条找不到哨兵 → 误判成用户拖拽。
- 修：新增纯函数 `grub_move_is_our_echo(position, placed)` —— 判据改成
  **持久的**「与最后一次我们要求它去的位置一致（±8px）就是回声」，不再作废；
  配套 `set_grub_placed_position` / `grub_placed_position` 两个打包/解包小函数
  （原来 u64 位拼装散在 3 处）。真被用户拖动时 GRUB 会离开该位置，>8px 后
  follow 照常触发 —— 方向功能不受影响（已用 `GRUBDRAG=1` 场景钉住）。
- `MAIN_FOLLOW_TARGET` 是一模一样的写法，但**故意不动**：它 fall through 后走的是
  `place_grub_list_window`，而 place 按主窗**当前**位置重算、结果与 GRUB 当前位置
  一致 → 幂等收敛；GRUB 那条 fall through 走的是 `follow_main_to_grub`，
  会去挪**另一个**窗口 → 正反馈。只有会形成反馈环的那条需要修。

## 回合 31：贴边「从左右缘左右拖动 → 主界面变长 + GRUB 窗乱闪乱跳」

用户报（Windows）：`从屏幕边缘左边左右拖动 / 从右边也一样 → 主界面会变长 还会导致 grub 窗口乱闪乱跳`。

### 先复现（新增复现台场景 DOCKPOKE=1，照用户动作分两段）
阶段 A「光标沿缘左右来回扫」（远端/条子上各停 0.8s）×3 个来回；阶段 B「贴边成条后直接抓边条
往工作区拖 200px」。左/右缘各跑一遍。采样**同时采主窗与 GRUB 窗**（只看 GRUB 分不清「正常 dock
节奏」与「互闪」，而「变长」只有主窗尺寸序列能证明）。
- 场景两个坑（写进 skill）：① 扫出必须**跨出「主窗∪跟随窗」并集**（跟随窗紧挨主窗，只扫到
  700px 还在它矩形里 → `inside` 恒 true → 贴边一次都没触发，于是「通过」其实没测）；
  ② 抓边条要先确认真的成条（先 windowmove 到缘上 + 光标停远 + 等 2.4s）。

### 根因（poke-1 实测，176ms/129ms 两条硬数字）
贴边成条 → 抓边条拖离停靠位 → `restore_main_dock_size` 把窗口展开回 460x900（**用户看到的
「主界面变长」**）→ **176ms 后** watcher 又按拖动途中的「光标在窗外」把它缩回条子；
GRUB 独立窗跟着可见性翻两次，**129ms** 内（**用户看到的「乱闪乱跳」**）。
- 判据两侧不对称：dock 分支早有 `docked_poll_action` 的 `busy → Hold`（我们自己刚发的几何
