## 修：Linux + NVIDIA 独显下主界面一片空白

**现象**：独显模式主窗空白、零报错；集显（Intel TigerLake）正常。

**定位**：本机 = Intel iGPU + RTX 3060 Laptop（615.71.09 开源内核模块）+ WebKitGTK **2.54.1**。
`strings /usr/lib/libwebkit2gtk-4.1.so.0` 确认 2.54 认 `WEBKIT_DISABLE_DMABUF_RENDERER`。
根因是 Tauri/WebKitGTK 在 NVIDIA 上的已知故障（tauri#9394/#10702、WebKitGTK Bug 280210）：
WebKit 的 **DMA-BUF 渲染器**跟 NVIDIA 谈不拢缓冲格式，构造不出完整 framebuffer 就静默放弃。

**改动**（三个文件）：
- `src-tauri/src/lib.rs`：新增 `apply_linux_gpu_workarounds()`（linux-gated），在 `run()` 最前面、
  `tauri::Builder` 之前调用。检测 `/proc/driver/nvidia/version`，按会话类型只加**一个**开关：
  X11/认不出 → `WEBKIT_DISABLE_DMABUF_RENDERER=1`；Wayland+Hyprland → 同上；
  Wayland+KWin/Plasma → `__NV_DISABLE_EXPLICIT_SYNC=1`；其它 Wayland+驱动≥560 → 不动。
  用户已设过四个开关中任一个就全跳过。`ANYBOOT_TRACE=1` 时往 stderr 打一行痕。
  纯函数 + 4 条单测（后端推断、NVRM 版本解析、选择表、逃生舱）。
- `README.md`：常见问题新增「窗口一片空白 / 只显示白色（Linux + NVIDIA 独显）」。

**验证**：`cargo test --release` **93 passed / 0 failed**；`cargo build --release` 出 `target/release/anyboot`。
Xvfb 冒烟：注入生效（stderr 有那行）+ WebKitWebProcess 的 `/proc/<pid>/environ` 里确实有该变量 +
新老行为截图渲染一致（无回归）。**真机 NVIDIA 结论仍待用户确认**。

**踩到的小坑**：`/proc/driver/nvidia/version` 第二行有 `gcc 16.2.1`，
宽松地扫「第一个带点的数字词」会把编译器版本当驱动版本 → 必须锚定 `NVRM version:` 那一行（单测抓到的）。

**顺带发现（未改）**：仓库整体 `cargo fmt --check` 不通过（cli.rs / grub.rs / http.rs / lib.rs 大量旧格式，
现在是 rustfmt 1.10.0、无 rustfmt.toml，属版本漂移）。只把自己新增的行格式化干净，没动别人的代码。

## 续：白窗修好后变成「只有鼠标扫过的地方才显示」

**现象**：关掉 DMA-BUF 渲染器之后，页面能加载了，但内容只在鼠标扫过的地方才画出来。

**定位**：这就是同一个病的第二种表现，不是新 bug。上游 WebKitGTK Bug 281279 的原话：
「HTML 不是没渲染，而是看不见；知道元素在哪、把鼠标移上去，光标形状都会变」，
结论是 `WEBKIT_DISABLE_DMABUF_RENDERER=1` **或** `WEBKIT_DISABLE_COMPOSITING_MODE=1` 任一能治。
关键是**不同驱动机器上真正生效的那个不一样**（GnuCash 2026 的反馈：原本管用的 COMPOSITING
在某版驱动后失效、换回 DMABUF 才行），所以不能赌。

**改动**：X11（含后端认不出）改成**两个开关都设**。
`X11_GPU_SWITCHES = [WEBKIT_DISABLE_DMABUF_RENDERER=1, WEBKIT_DISABLE_COMPOSITING_MODE=1]`；
`linux_gpu_env_override()` → `linux_gpu_env_overrides()`（返回切片，一条到两条）；
调试点那行改成把设上的开关全打出来。Wayland 各支不变（只设一条）。
代价可忽略：本应用全局无 WebGL / canvas / 重动画，UI 是静态面板。

**验证**：93 passed / 0 failed；Xvfb 下两个变量都设上且都传到了 WebKitWebProcess；
关掉加速合成后界面渲染完整（透明、圆角、下拉框都在），无回归。
**真机结论仍待用户确认**。

**回归面查全了（关掉加速合成是全局开关，三个窗口都得看）**：
- 主窗：完整（系统引导那屏：下次启动卡、三个系统卡、GRUB 区块、下拉框、按钮全在）
- 通知弹窗：用 `POST /api/power?action=reboot`（配 `ANYBOOT_POWER_DRY_RUN=1` + `channels.*.delaySeconds=60`
  留截图时间）调出来 → 标题/来源/进度条/「55 秒后自动执行」/双按钮/提示小字全部正常，
  **没有**复现历史上的「0 宽视口折成竖条」
- 贴边白条：`ANYBOOT_AUTOHIDE_DIAG_FORCE_DOCK_MS=2500` 触发（trace `dock edge=Top target=(0,0)`，
  窗口 460x40）→ 纯白条正常，无残缺
- 沙箱设置文件字段名（照抄省事）：`mainAutoHide` / `channels.{http,cli}.{notify,delaySeconds}` /
  `httpBind` / `httpPort` / `httpToken` / `mainDockStrip*`

**定则**：以后凡是「WebKitGTK × NVIDIA 画不出来」类问题，先想「这两个开关是不是都该设」，
别只设一个就以为修好了 —— 只设一个的典型结局就是换个毛病（全白 ↔ 只有鼠标扫过才显示）。

## 第三轮（终版）：真机反馈「还是只有鼠标扫过才显示」→ 前两条定则作废

用户真机跑 `ANYBOOT_TRACE=1 ./anyboot` 回贴：

```
anyboot: NVIDIA 驱动 615 / X11，已设置 WEBKIT_DISABLE_DMABUF_RENDERER=1 WEBKIT_DISABLE_COMPOSITING_MODE=1
```

分支挑对了（X11 / 驱动 615 / 两个开关都设上），但**症状与只设一个时一字未变** —— 这就是线索：
`WEBKIT_DISABLE_COMPOSITING_MODE` 压根没起作用（**上面「两个都设」那条定则作废**）。

**取证（三份独立来源互证，都指向同一个开关）**：
- WebKit **Bug 324551**（2026-10-03，十天前的报告）：NVIDIA 机上「关掉合成后页面仍是空白」，
  **唯一能把页面画出来的是 `WEBKIT_DMABUF_RENDERER_FORCE_SHM=1`**；并明说 2.54 起非合成渲染器
  也走 AcceleratedBackingStore，所以 `DISABLE_COMPOSITING_MODE` 已不避开该问题。
- **Buzz 桌面端 #3271/#3654**：检测到 NVIDIA（`/sys/class/drm` 下 vendor `0x10de`）就自动设
  `FORCE_SHM=1`，并**明确「切勿使用 `WEBKIT_DISABLE_DMABUF_RENDERER=1`」** —— 2.52+ 该变量不再
  回退到共享内存，传输模式变空、`AcceleratedBackingStore::create()` 返回 null，会 SIGSEGV。
- **A2Tools DPS Meter** 的 Linux 说明：同症状（只画一部分 / 悬停才画），修法同为 FORCE_SHM，
  并要顺手去掉 DISABLE_DMABUF_RENDERER。

**为什么症状会「演化」**：WebKitGTK 2.46 起 Skia 取代 Cairo 做 2D；**2.54 起连合成器也换成 Skia，
并把「只合成损伤区域」打开成默认** —— 帧更新改由 damage 驱动，NVIDIA 下就表现成「只有鼠标扫过才重绘」。
（本机 2.54.1 库里 `WEBKIT_DISABLE_COMPOSITING_MODE` 字符串还在，但已是空壳 —— *字符串存在 ≠ 生效*。）

**落地**：`X11_GPU_SWITCHES` 换成单条 `WEBKIT_DMABUF_RENDERER_FORCE_SHM=1`；单测把开关集钉死、并新增
断言禁止那两个废弃名回到 X11 支。Wayland 各支**未动**（无实机证据），只在 `DMABUF_RENDERER_OFF` 注释里
记下「Hyprland 若也反馈空白/崩溃，同样该换 FORCE_SHM」。README 表格与说明同步。

**验证**：93 passed / 0 failed；Xvfb 下 trace 显示新开关、渲染子进程 `/proc/<pid>/environ` 实测继承到、
进程不崩、界面渲染完整无回归。**NVIDIA 真机效果仍待用户确认。**
备选（未验证，按序试）：`WEBKIT_DISABLE_DMABUF_ATLAS=1`（2.54 新增的 GPU atlas）、`LIBGL_ALWAYS_SOFTWARE=1`。

**新定则**：动 WebKitGTK 渲染开关前，先确认**这个开关在你的 WebKit 版本上还有没有效** ——
2.46 / 2.54 两次架构变更作废了一批老开关，照着旧帖子「加一个开关」在新版上可能等于什么都没做。
判断开关是否真的生效的硬标准：**换开关后症状必须"变"**（哪怕变坏）；症状一字不变 = 空壳。

**三窗口回归（换开关后重跑 —— FORCE_SHM 动的是「帧怎么交付给窗口系统」这条全局路径，
所以主窗之外那两个独立 WebView 必须重验）**：
- 主窗：完整（系统引导屏全部元素）
- 贴边白条：`ANYBOOT_AUTOHIDE_DIAG_FORCE_DOCK_MS=10000` → trace `[autohide] dock edge=Top target=(180,0)`、
  几何 460x40，截图是干净的纯白条（bar.png 只 311 字节 —— 画面绝大部分是纯黑、压缩率极高，别被字节数骗了）

  `channels.*.delaySeconds=90`）→ trace `[notify] present height=246`，弹窗完整（标题 / 来源行 / 进度条 /

**③ 客户端「有时候一片空白」的根因与修法**
根因：`probeRemoteApi()`（探 `/health`）**只在初始化跑一次**，失败即把 `remoteApiAvailable` 永久定为 false
→ 页面进「纯预览模式」：横幅说预览、正文永远空着，且 `listen("ui-state-changed")` 那一刻返回空函数、
**连轮询都没起**，只能手动刷新。客户端刚打开时电脑端正在重启 / 网络刚通，正好命中这个窗口。
修法：`scheduleRemoteApiReprobe()` 每 2s 重试到探通；探通后 `attachRemoteApi()` 重挂横幅 + 引导 token +
起轮询（`startUiStatePolling()` 单例，已从 `listen` 内联抽出，handler 存 `uiStateHandler`）+ 取首份快照。
兜底：`applySnapshot` 遇结构不对的快照不再静默 return —— 从未成功渲染过时给一条状态条提示。

**12:35 改尺寸后不居中（新默认「固定屏幕中间」暴露出来的 bug）**
- 现象：`set_size` 是**以左上角为锚**改尺寸的，只改高度时窗口往下长出去 → 底边越过工作区 →

  （窗口中心 540 漂到 360）。用户拖一次高度滑条就中招 —— 这正是新默认「固定显示位置屏幕中间」
  名不副实的地方。
- 修法：`set_main_window_size` 末尾调新函数 `recenter_after_window_size(app, width, height)`：
  ① 只在窗口**已显示**时插手（启动期 setup 那条路径有自己的「等 WM 映射完再落位」自愈流程，
     抢跑会被 WM 忽略/覆盖）；

**13:00 挖出第二个真 bug：电脑端一重启，已开着的客户端永久冻在旧快照上（已修）**
- 起因：想验「服务重启后页面能不能自己接回来」。设计要点 —— **让恢复可观测**：
  断线期间把宿主状态改掉（删 `PreviousBoot-windows` + 把 `settings.json` 的 theme 改成 dark），
  重连后页面若真拿到新快照，就该出现「（不存在）」+ 按钮变灰 + 深色主题。
- **两个自设的坑（记下来省时间）**：
  ① 第一版标记用错了 —— 变量文件被删**不会**让卡片消失，只让副标题多出「（不存在）」、按钮变灰
     （`renderSystems` 里 `item.exists ? ... : \`${item.sourceName}（不存在）\``）；
  ② 结果解读必须分辨「没重连」还是「重连了但快照旧」—— 所以要独立标记。
- **现象定位**（关键工具：给页面的 `fetch` 装钩子，记录每次请求的结局）：
  - 断线期间：`{'url':'/api/ui-state','state':'ok','status':502}`（代理给的错误响应，不是异常）；
  - 重启后：**每 2 秒都是 `state:'ok', status:200'`，页面却一个字段都不更新**；
  - `visibility=visible / hidden=False`（不是后台页被暂停）；`fetchCount` 持续增长（轮询在跑）；
  - 先用 `live.py` 隔离：**连接正常时实时更新是通的**（宿主改 light→dark→light，页面跟着变），
    所以 handler / token / 轮询都没问题 → 问题只在「拿到快照后拒不应用」那一支。
- **根因**：`ui/app.js` 的 `applySnapshot` 有 `if (!force && state.revision <= lastRevision) return;`
  —— 用 revision 丢过期快照本身没错，但 **revision 是「进程内」计数器**（`UI_REVISION` 从 0 起）。
  进程一重启又从 0 数起，客户端手里「旧进程的高水位」就把新进程的快照**全部**丢弃。
  数值实证：旧进程 revision 涨到 **7**（客户端 lastRevision=7），新进程只到 **5** → `5 <= 7` →
  永久冻住。旧进程跑得越久（revision 上千），新进程越不可能涨过去 → 实际等于「不刷新页面就永远不同步」。
  症状是「越用越不同步」，用户根本不会联想到「我重启过 AnyBoot」。
- **修法**（后端一行 + 纯函数）：`UI_REVISION` 的起点改成**启动时刻的 Unix 毫秒**
  （`ui_revision_seed(unix_millis())`，在 `run()` 里**第一件事**就 store，必须早于任何 `publish_ui`）。
  新进程启动更晚 → 起点必然更大 → 客户端继续比大小就自然接受，**所有客户端（网页/手机）都不用改**。
  单测 `ui_revision_seed_must_not_restart_from_zero` 钉住「不能从 0 起 / 越晚启动种子越大」。
  副作用：trace 里 `[state] revision=` 变成 1.79e12 量级的大数，不影响任何逻辑（revision 不展示给用户）。
- **修复后同一脚本实测**：`[after] 卡片: Windows PreviousBoot-windows（不存在）`、

  断线期间也不崩、不变空白（保留最后一次快照）。**100 passed / 0 failed**，二进制 12:59 重建。

## 传输方式（WebSocket 推送 / HTTP 轮询）+ 手动刷新 / 下拉刷新（15:48–16:05）

**需求**：移动端要能选 WebSocket / HTTP 两条通道；HTTP 那条要手动刷新 + 下拉刷新。

**定案**
- 后端新增 `GET /api/ws`（**WebSocket 推送通道**，与 `/api/ui-state` 送**同一份** `ui_state_json()`，
  只是「谁先知道」不同）：tiny_http 的 `Request::upgrade` 做 RFC6455 握手
  （`Sec-WebSocket-Accept = base64(SHA1(key+GUID))`，协议写死 SHA-1 → 引 `sha1` + `base64` 两个 crate），
  `WS_CLIENTS: Mutex<Vec<(u64, SyncSender<String>)>>` 订阅表，`publish_ui` 里广播（队列满**丢帧不阻塞**，
  `WS_QUEUE = 8`）。首帧直接就是**完整快照**（连上即可渲染，不必再 GET 一次）。
  鉴权复用 `http_token`：握手吃不到自定义头，所以是 `?token=` / `anyboot_token` cookie（`WS_TOKEN_COOKIE`，与前端同名）。
- **只写不读**：`upgrade` 交回的是 `Box<dyn ReadWrite + Send>`（读写在同一个对象里 box 着，拿不到 TcpStream，
  也没法设读超时），而「读对端帧」和「发快照」必须并发。所以放弃读 —— 这条通道本来单向。
  代价：对端消失只能从**写失败**上发现 → 空闲 25s 发一个 ping 当**唯一探测器**（`WS_KEEPALIVE`）。
- 前端三档 `transportMode`：`auto`（默认，推送优先、失败落轮询并后台退避重连）/ `ws` / `http`。
  `auto` 时推送一通就 `stopUiStatePolling()`（两条一起跑 = 做两份功 + 互相覆盖）；
  用户明确选了 `ws` 就**不许偷偷改回轮询**（只提示「正在重连…」）；退避 1s→2s→…→30s。
- **`?transport=` 必须由 App 从 URL 带过去**：网页 `localStorage` 按**来源站点**（IP）存，
  而一台电脑多网卡会换地址（= 换来源），只存网页端偏好会丢。空值/`auto` 不加参数。
- 刷新：`refreshNow()`（横幅「刷新」按钮 + 下拉刷新共用）走 `/api/ui-state` + `applySnapshot(force:true)`
  —— force 是为了「用户要的是看得见的反馈」；`installPullToRefresh()` 用**非 passive 的 touchmove +
  preventDefault**（不拦会被浏览器当成整页回弹刷新，两套叠一起），只在**真的在顶部**时接管手势。

**验证（这次做得比较硬）**
- Rust：`cargo test --release` → **110 passed / 0 failed / 1 ignored**（WS 新增 6 条：RFC 示例 accept key、
  三种长度形式的帧编码、升级请求识别、cookie 取 token、订阅表增删 + 不阻塞掉帧）；`cargo build --release`
  → 15,598,400 B。

## 16:48-17:02 · 排查「AppImage 换机器报 GLIBC_2.43/2.44 not found」

**根因**：AppImage 把构建机（CachyOS，**glibc 2.44**）的整条 GTK/WebKit 依赖链裹进去了
（184 个 .so / 283MB），目标机 glibc 比 2.44 老 → 加载那些库就报缺版本。**与应用本体无关**：
`objdump -T` 量出来本体 `usr/bin/anyboot` 只要 **2.39**，而 `libwebkit2gtk-4.1.so.0` /
`libjavascriptcoregtk-4.1.so.0` 要 **2.44**，另有 9 个库要 2.43。
**判据**：用户报错里没有一行 `required by usr/bin/anyboot` → 他系统 glibc 已 ≥2.39。

**纯配置无解**：linuxdeploy-plugin-gtk 只认 `DEPLOY_GTK_VERSION` 等几个变量，没有 exclude-library；
tauri-bundler 也不透传。（别再去翻 tauri.conf.json 找了。）

**已产出一个实验产物**（在 `~/.cache/ab-appimage/`，**没动项目里任何配置**）：
删掉 `AppDir/usr/lib/*` + `usr/lib64`，把 AppRun 会 source 的 GTK hook 置空 → 重打成
`AnyBoot-portable-x86_64.AppImage`。整包最高 glibc 需求 **2.44→2.39**，体积 **105MB→4.1MB**。
重打法子（本机没 FUSE、也下不动 runtime）：从插件 AppImage 里 `--appimage-extract` 掏出自带的
appimagetool+mksquashfs，再从现有 AppImage 抠出 runtime 头（squashfs 魔数 `hsqs` 的偏移 = 194183），
`appimagetool --runtime-file` 重打。

**没验到的（关键，不许算成功）**：本机**跑不起**这个应用 —— 拿**原版**（完整库）AppImage 做对照，
在本机同样崩（`Failed to initialize GTK` / `Rust cannot catch foreign exceptions`）；
`Xvfb :98` 更直接崩在 `libnvidia-egl-gbm.so.1`，加软件渲染也没救回来。
→ 本机 Xvfb + NVIDIA 不具备 AppImage 图形验收能力，**「删库版能否启动」在本机没有区分力**，
只能在报错那台机器上验。

**给用户的两条路**：A 不裹 GTK/WebKit（=上面的产物，目标机需自带 webkit2gtk-4.1）；
B 在 glibc≥2.39 的基座重建（保持自包含；本机 docker daemon 没跑，做不了）。
用户侧还有个不用等我打包的自救：解包后删 usr/lib + 清空 GTK hook 再跑 AppRun。

## 二进制补丁 SEGV 修复（第二轮用户反馈）
