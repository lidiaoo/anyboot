## AnyBoot 托盘/远程/主题四连修（用户实测反馈）

1. **Windows 子进程弹控制台窗口**：GUI 程序 spawn 控制台程序（提示音走 powershell、
   端口诊断走 netstat/wmic、电源走 shutdown/rundll32/powercfg、taskkill）时 Windows 会
   新建一个控制台窗口，表现为倒计时弹窗旁边闪出的蓝色 PowerShell 窗口。
   修法：lib.rs 顶部加唯一入口 `fn command(program) -> Command`，Windows 下带
   `CREATE_NO_WINDOW`（0x0800_0000）；全文件 13 处 `Command::new` 全部改走它。

2. **token 与「远程怎么调」不联动**：示例里的 token 是启动时取一次，改完 token 面板
   还是旧命令（看起来像"没重新监听"）。后端 `set_http_token` 其实有走 `apply_http_config`。
   修法：前端 `refreshHttpHintIfChanged(http)` 用「打码 token / bind / port / listening / addr」
   做 key，变化就重新 `invoke("http_access_hint")`。**注意**：明文 token 不能进快照
   （后端契约：快照只放打码版），所以只能靠派生字段判断。
   同时 `HttpView.state_text` 抽出 `http_state_text()`，主窗口 `#http-state` 与托盘
   「远程控制」子菜单共用同一句话。

3. **亮色主题文字不显眼**：styles.css 的 `[data-theme="light"]` 灰阶整体压暗
   （text-dim #3c4654 / faint #4c5665 / fainter #626c7b），输入框描边加强；
   notify.css 补 light 变体，notify.js 按快照里的 theme 写 data-theme。

4. **托盘菜单**：顶部新增「下次启动：X」项（id `next-boot` → MenuAction::Show）；
   系统列表改成 `IconMenuItem`，选中行带**生成的 16×16 绿勾位图**（`check_mark_rgba()`，
   颜色与 --ok #46c46e 一致），去掉「● 」前缀 → 名称列左对齐；
   电源操作铺平（不再折叠成子菜单）；「远程控制」子菜单首行加监听状态。
   `menu_signature` 增加 `http_state` 参数，并把 httpEnabled / notifyEnabled /
   两条渠道的 delay 纳入指纹（以前主窗口改设置，托盘勾选不刷新）。

验证：`cargo test --release` 46 passed（debug 配置在本机因 schemars 0.8.22 编译失败，
与本次改动无关，用 release 配置验证）；`node --check ui/app.js ui/notify.js` 通过。

模型/工具注意：`tauri::image::Image` 的 `rgba()` 需要 `&'static self`，借不出局部变量 ——
所以位图生成拆成纯函数 `check_mark_rgba() -> Vec<u8>` 便于单测。

## 第二轮（用户复报：托盘分区 / token 重启 / 主题对比度 / 弹窗闪位）

1. **托盘菜单重排成分区**：新增 `menu_section_header()` —— 原生菜单没有分组概念，
   只能用「灰掉的标题项 + 上下两条 `PredefinedMenuItem::separator`」表达分区。
   现在结构：顶部「下次启动：X」（绿勾、可点）→ 系统列表 → 显示主窗口 → 应用设置 → 扫描
   → **电源操作**（铺平 + 标题）→ **远程控制**（铺平 + 标题，第一行就是监听状态）→ 退出。
   要点：远程控制**不再是 Submenu**，监听状态从子菜单里提到了主菜单层级。

2. **「下次启动」重复**：扫描成功后 `status.message` 本身就是「下次启动：X」，
   和顶部那行一字不差 → 菜单里出现两条。抽纯函数 `menu_status_line(message, next_boot_label)`
   （相同/空白 → None，否则 Some(trim)），并单测覆盖。

3. **token 变更要真重启端口**：原来的 `update_settings_and_publish` 文案在重启**之前**就定死了
   （写「监听已按新 token 重启」，是假设不是事实）。新增
   `update_settings_and_restart_http()`：save → `apply_http_config`（内部先 stop 再 start）
   → `http_listener_summary()` 拿真实结果（「监听已重启：addr」/失败原因）当状态文案。
   `set_http_token` / `regenerate_http_token` 改走它。
   实测确认：Windows 上 TIME_WAIT 不会挡住同端口重绑（用 Python 造服务端主动关闭 + netstat 验证），
   所以停-启是可靠的，问题只在「用户看不到有没有真的重启」。

4. **主题对比度 / 透明度下看不清字**：根因不只是灰色太浅 —— `.directory` / `.settings`
   以前**只有一条上边框、没有底色**，正文直接压在半透明窗体背景上，不透明度一低就糊。
   修法：两个区改成带 `--panel` 底色的卡片；四档灰阶整体拉开
   （dark: text #f3f6fb / dim #c4cddd / faint #b2bed1 / fainter #98a5ba；
   light: #0c1017 / #2c3543 / #3b4553 / #505b6b）；给**不在卡片里**的 `h1` / `#status` / `#message`
   加 `text-shadow: var(--text-shadow)`（dark 黑描边、light 白描边）。

5. **弹窗先在左上角闪空白再跳右下角**：原因是 `WebviewWindowBuilder` 默认 **visible(true)**，
   建出来先按系统默认位置画一帧，再 `set_position` 跳走。
   修法：`.visible(false)` + `.on_page_load(...)`，等 `PageLoadEvent::Finished` 再
   `position_notify_window()` → `show()`；尺寸常量 `NOTIFY_WIDTH/HEIGHT` 与定位共用。
   同时抽出 `position_notify_window(app, window)`（current_monitor → primary_monitor 回退）。

前端：app.js 加 `refreshSnapshotQuietly()`；token 保存/重新生成后不再写死「已重启」，
改用后端如实上报的状态文案。README 同步。

验证：`cargo test --release` **47 passed**（新增 tray_status_line 测试）；`node --check` 通过。

## 第三轮（用户复报：点「重新生成」报 10048）

**先纠正上面第 3 条的结论**：当时只测了 TIME_WAIT，结论「停-启是可靠的」是错的。

真根因：`tiny_http::Server::drop` 只做两件事 —— 置内部 `close` 标志，然后
`TcpStream::connect(listening_addr)` 去唤醒它自己的 accept 线程。而 `listening_addr`
来自 `TcpListener::local_addr()`，绑 `0.0.0.0` 时它就是 `0.0.0.0:12300` —— **通配地址**。
本机实测：Windows 上 `connect(0.0.0.0:port)` = **WinError 10049**（地址无效），
`connect(127.0.0.1:port)` 才通。也就是说 accept 线程永远收不到唤醒，永远卡在 `accept()`，
它手里的监听 socket 永远不关 → 本进程再也绑不上 12300，报 `os error 10048`，
必须退出程序才能恢复。Linux 上 connect(0.0.0.0) 被当 127.0.0.1，所以这个坑只在 Windows 现形。

另外两个衍生事实：
- `is_self`（pid == 自己）为真时，`PortOccupant::display()` 也因为走了 `same_app` 分支
  而显示成「本应用的另一个实例」—— 用户会去找一个不存在的进程。已按三类分开写文案。
- 前端此刻还会渲染出「结束 PID 自己」的按钮（后端会拒绝）。已按 `isSelf` 隐藏。

修法（http.rs）：`RunningServer` 增加 `wake: Vec<SocketAddr>`（从**实际绑上**的地址算：
通配→同族回环，再兜一个 127.0.0.1）与 `probe: (String, u16)`；`stop()` 变成
「置标志 + wake → join（tiny_http Drop 在此跑）→ **再 wake 一次** → `wait_until_released()`
轮询试绑（5ms × 2s 上限）」，返回 `Result<(), String>`，即 **stop() 返回 == 端口已放开**。
判定「已放开」靠「我们自己能 bind 上」，试绑的 listener 立刻丢掉（没 listen 过，无 TIME_WAIT）。

同时删掉 `apply_http_config` 里那段「勾选开启时立即重试一次」的 `diagnosised` 块 ——
它的注释把原因猜成 TIME_WAIT，实际是同进程 socket 泄漏，重试不可能成功（用户偏好：主方法足够就删冗余兜底）。

验证：`cargo test --release` **50 passed**。新增三条：
`wake_addrs_replace_wildcard_with_loopback`、
`wait_until_released_reclaims_a_wildcard_port`（真 tiny_http 绑 0.0.0.0:0 + 100ms 确保 accept 已阻塞
+ drop + 等收回）、`connecting_to_the_wildcard_address_fails_on_windows`（根因钉子，cfg windows）。
**关键验证**：把 `wait_until_released` 里的 wake 临时注释掉后跑目标测试，报的正是
`0.0.0.0:13571 … (os error 10048)` —— 与用户截图一字不差，确认这条修复是承重的，不是装饰。

坑：本机 **debug** 配置编译挂在依赖 `schemars 0.8.22`（既有环境问题，与改动无关），
一律用 `cargo test --release` 验证。

## 第四轮（用户复报：弹窗/托盘压任务栏、两个框色调、不透明度 0-100、按钮顺序）

**A. 弹窗高度按内容自适应**：`NOTIFY_HEIGHT` 从 320（写死）改成**标称** 240，新增
`NOTIFY_MIN_HEIGHT=150 / NOTIFY_MAX_HEIGHT=460`。窗口仍是 `.visible(false)` 建出来，但**不再**
在 `on_page_load` 里显示；改为前端量高度 → `invoke("present_notify_window", {height})`
→ 后端夹取（纯函数 `notify_height(Option<f64>)`，None/0/NaN 退回标称）→ `set_size`
→ `place_notify_window` → `show()`。Rust 侧留 800ms 兜底线程（前端脚本万一没跑起来，
`is_visible()` 判一下再按标称高度露出来）。
量高度的法子（notify.js `measureContentHeight()`）：取 `.panel` 最后一个有高度的子元素，
`last.bottom - panel.top + paddingBottom + borderBottomWidth` —— 与窗口当前高度无关，
所以隐藏状态下也能量准。`.panel` 加了 `overflow-y: auto`，超长内容宁可出滚动条也不裁掉按钮。

**B. 弹窗不压任务栏**：定位改用 `Monitor::work_area()`（`PhysicalRect{position,size}`）而不是
`size()`；尺寸用**我们要设成的逻辑高度**换算（`set_size` 是异步投递的，设完 `outer_size()`
读回还是旧值 → 位置会偏几十像素）。

**C. 托盘右键菜单不压任务栏（Windows）—— 本机实测过的根因**：
tray-icon 的 `show_tray_menu` 是 `TrackPopupMenu(menu, TPM_BOTTOMALIGN|TPM_LEFTALIGN, cursor.x, cursor.y)`
（源码 `tray-icon-0.24.2/src/platform_impl/windows/mod.rs:542`），锚点是**光标**，而托盘图标的光标
就在任务栏里。用 Python ctypes 复刻三种情形（同一线程里 CreateWindowEx+CreatePopupMenu+TrackPopupMenu，
主线程 `FindWindowW("#32768")` + `GetWindowRect` 量，`PostMessage(WM_KEYDOWN, VK_ESCAPE)` 收场）：

| 用例 | 锚点 | 菜单 rect | 越界 |
| --- | --- | --- | --- |
| tray-icon 原样 BOTTOMALIGN | (2074,1214) 光标在任务栏里 | 2050,944–2194,1214 | **压 20px** |
| muda 原样 LEFTALIGN | 同上 | 同上 | **压 20px** |
| 锚在工作区底边 | (2074,1194) | 2050,924–2194,1194 | 0px |

结论：**Windows 只保证菜单不越出屏幕、不保证不越出工作区**，换标志位没用，只能换锚点。
本机：屏幕 2194×1234、工作区底 1194、任务栏 40px。

改法：Windows 上**托盘不挂菜单**（`tray_builder.menu()` 用 `#[cfg(not(target_os="windows"))]` 包起来），
右键事件里现建现弹：`popup_tray_menu()` 用 `monitor_from_point()` 拿工作区，目标点 =
(cursor.x, work.bottom)，再 `menu.popup_at(anchor, target - anchor.outer_position())`。

Tauri 侧的三个坑（都踩过）：
1. `AppHandle::get_window` / `Manager::windows()` 被 tauri 的 **`unstable` feature** 挡着，
   公开的只有 `get_webview_window` → 锚点得是 **WebviewWindow**（`ui/menu-anchor.html`，
   8×8、无边框、不可见、创建时 `.position(0.0,0.0)`）。
2. `Window<R>` **不是 Send/Sync**（内部挂着 muda 菜单 `Arc<Mutex<Option<WindowMenu>>>`，muda 是 Rc），
   进不了 `app.manage()` —— 所以别想着把它存 state 里。
3. `popup_at` 在公开 trait `tauri::menu::ContextMenu` 上（要 `use`），它把坐标当**锚点窗口的客户区
   坐标**再 `ClientToScreen` 一次；无边框窗口客户区原点 == 窗口左上角，所以传「屏幕坐标 − 窗口原点」正好。
   `WebviewWindow::as_ref().window()` 能拿到底层 `Window` 句柄（公开 API）。
另外确认：托盘 `on_menu_event` 是**全局**菜单事件监听器（tauri 源码注释原话：any menu event,
whether from this window / another window / tray icon menu），所以自己弹的独立菜单照样能派发到它。

**D. 「远程怎么调」与「最近请求」框色调统一**：`#http-requests` 原先是裸列表，现在与
`.remote-hint pre` 共用一套「描边 + 圆角 8 + `--input-bg` 底 + `--text-dim` 字 + 11px」，
只有 padding 不同（列表左边留 26px 给序号）。

**E. 不透明度 0–100**：`MIN_OPACITY` 50 → 0，滑块 `min="0"`，app.js `Math.max(0, ...)`，
`set_opacity` 注释同步。0% = 全透明但窗口还在（托盘照常操作）。

**F. 「打开变量目录」挪到「使用此目录」左边**（index.html 按钮顺序）。

验证：`cargo test --release` **51 passed**（新增 `notify_height_is_clamped_and_falls_back_to_nominal`，
并改了 opacity 断言：0/1 现在是合法值），零警告；`node --check` 通过。
**运行时未能在本机实测**（右键托盘要人工操作；且用户此时有旧实例 PID 3324 占着 12300 与 exe 文件锁）。

模型/工具注意（可复用）：
- 探测 Windows 原生菜单几何的 ctypes 配方见 `.workbuddy/tmp_menu_probe.py` / `tmp_anchor_probe.py`
  —— **建窗口、建菜单、TrackPopupMenu 必须在同一个线程**，否则 `TrackPopupMenu` 直接返回 0
  （跨线程建窗口那次报的是 1400 ERROR_INVALID_WINDOW_HANDLE）。
- `SPI_GETWORKAREA` 拿工作区；`FindWindowW("#32768", None)` 找到菜单窗口；`GetWindowRect` 量它。

## GRUB 跨端切换可行性调研（读 arch-gui:/boot/grub/grub.cfg 实测）

用户想把 linux 的 system-switch.sh（GRUB/kexec 切系统）移植进 AnyBoot 三端通用。
本轮只做「能否从 Windows 读到 ext4 上的 grub.cfg」的实测，**不改项目代码**。

**本机磁盘事实**（`Get-Partition` + `Win32_Volume` 全量枚举，diskN=0 共 22 分区）：
- ext4 分区（GPT type `0fc63daf-8483-4772-8e79-3d69d8477de4`）：2,3,7,8,10~14,16,18,20,21 —— 全部无盘符
- 有盘符的卷只有：C/D/E/J（NTFS）、H/R/S/U（FAT32）。`H:` 卷标 = `ARCH-EFI`（但里面只有 `EFI/`，无 boot/grub）
- `arch-gui` 卷标**不在**任何已挂载卷里 → 它是某个无盘符 ext4 分区

**四条读取路径全部堵死，根因同一个：当前进程非管理员（IsUserAnAdmin=0）**
| 方案 | 结果 |
| --- | --- |
| 裸读 `\\.\PhysicalDrive0` / `\\.\HarddiskVolumeN`（ctypes CreateFileW）| `err=5 ERROR_ACCESS_DENIED`，非管理员打不开任何裸设备句柄 |
| `wsl --mount '\\.\PhysicalDrive0' --bare` | `WSL_E_ELEVATION_NEEDED_TO_MOUNT_DISK`（必须 Windows 管理员，WSL 内 root 不算） |
| `Add-PartitionAccessPath` 给 ext4 分区分配盘符 | 「无法从客户端中访问 CIM 资源」= 需管理员 |
| MSYS 下 `dd if=/dev/sda1` | Permission denied（MSYS 的 /dev/sd* 只是模拟节点，读不了宿主磁盘） |
- WSL 里能看到 `/dev/sda~sdd`，但都是 WSL 自己的虚拟盘（722MB/98MB/12GB/154MB），**不含宿主机 22 分区那块盘**
- `wsl.exe` 已在黑名单外（用户已放行），但 `wsl --mount` 仍需 Windows 管理员
- `Start-Process -Verb RunAs` 触发 UAC 被 WorkBuddy 安全策略拦截，自动化环境无法提权

**结论**：Windows 侧读 ext4 的硬门槛就是**管理员权限**。要么以管理员运行、要么装 ext4 驱动分盘符，
两条都必须用户手动操作，程序无法自动绕过。这印证了方案设计里「ext4 访问是特权依赖」的判断。

### 本机已装的 ext4 工具（用户已装，供后续复用）
- **Ext2Fsd**：`D:\Program Files\Ext2Fsd\`（`Ext2Mgr.exe` GUI + `Ext2Srv.exe` 服务 + `Ext2Fsd.sys` 驱动）
  - 服务 `Ext2Srv` = Running，驱动 `Ext2Fsd` = Running（`HKLM\SYSTEM\CCS\Services\Ext2Fsd`，Parameters: AutoMount=1, WritingSupport=1, Ext3ForceWriting=1）
  - 但 `Ext2Fsd\Volumes` 子键**为空** → 一个 ext4 分区都没挂上（自动挂载也需要管理员）
  - `\\.\Ext2Fsd` 设备句柄存在但打开返回 err=5 → 同样被管理员门槛挡住
  - 包内**没有**命令行 `mount.exe`（只有 Ext2Mgr GUI）
- **DiskInternals Linux Reader**：`D:\Program Files (x86)\DiskInternals\LinuxReader\`（`LinuxReader64.exe` / `LinuxReader.exe`）
  - **纯 GUI、无 CLI 导出接口**、无内核驱动（`av/` 只是 ffmpeg 类 DLL）→ 靠用户态扇区读，脚本无法调用它取内容
  - 默认不分配盘符（浏览式），用户需在 GUI 内手动「Save」导出文件
- 也就是说：**两个工具都装好了，但光装好并不会让 ext4 分区变成可读路径**，仍需一次管理员动作
  （Ext2Mgr 里手动挂载 / Linux Reader GUI 内操作 / 管理员跑 wsl --mount）。

### ★ 突破：ESP 上就有 grub.cfg，完全不需要 ext4 工具（实测成功）
- 路径：**`H:\EFI\arch-efi\grub.cfg`**（`H:` = `ARCH-EFI`，FAT32，ESP 分区）
  - 同目录还有 `grubx64.efi` + 6 个 `grub.cfg.backup.*`（用户自己的备份习惯）
  - **直接 `head`/`grep` 读全了 44KB，全程零 ext4 依赖、零提权** → 印证「先扫 ESP」策略正确
- 该 grub.cfg 结构（pid 方案要移植的解析目标）：
  - `$prefix` 指向 ESP 的 grub 目录；`if [ -s $prefix/grubenv ]; then load_env; fi`
  - `next_entry` 机制：设 `default="${next_entry}"` → 清空 next_entry → `save_env next_entry` → `boot_once=true`
  - 否则 `default="${saved_entry}"`；`savedefault()` 函数把 `chosen` 写入 `saved_entry`
  - 顶层 menuentry + `$menuentry_id_option 'gnulinux-...-<UUID>'` 形式给 id

  11. OpenCore (macOS)  ← chainloader /EFI/BOOT/BOOTx64.efi, search UUID A5EB-573A
  12. Windows Boot Manager  ← osprober-efi-0802-080E, chainloader /efi/Microsoft/Boot/bootmgfw.efi

## GRUB env 外置（grubenv 放 FAT32）官方支持性调研

**结论：官方原生支持**，三条机制（都能把 grubenv 放到 FAT32 ESP）：
1. `load_env [--file FILE]` / `save_env [--file FILE]` —— 官方手册 §17.4.52 / §17.4.78，
   原文「The `--file` option overrides the default location of the environment block」。
   默认位置是 `$prefix/grubenv`（手册 §15.2 明确「normally lives in /boot/grub/grubenv
   (although you should not assume this)」）。FILE 可用 `(hd0,gpt2)/grubenv` 形式。
2. `env_block` —— 手册 §15.3 把它列为「Special environment block variable」之一
   （另两个是 saved_entry / next_entry）；§15.3.3 定义：值用 **GRUB blocklist 语法**
   （如 openSUSE 的 `512+1` = 扇区偏移+扇区长度），为 **Btrfs 保留区**设计，
   由 grub-editenv 创建 grubenv 时初始化并当成只读。
3. 上游补丁（2025-09/10，SUSE Michael Chang，Neal Gompa review）把 env_block 接进
   `00_header.in`：`if [ "${env_block}" ]; then set env_block="(${root})${env_block}";
   export env_block; load_env -f "${env_block}"; fi`，并把所有 `save_env` 改成
   `save_env -f "${env_block}"`（回退到 grubenv）。
   **用户的 Arch grub.cfg 里已含这段代码**（备份第 11-28 行、53-57 行），即无需重新生成配置。

**实践先例**：
- RAUC 官方文档：UEFI 系统建议把 grubenv 放 ESP（如 `/EFI/BOOT/grubenv`），
  并在 grub.cfg 里改 `load_env --file=(hd0,2)/grubenv` / `save_env --file=…`。
- Fedora/openSUSE：`/boot/grub2/grubenv -> ../efi/EFI/fedora/grubenv` 软链到 ESP。
  坑：`/boot` 未挂载时相对软链会落到 ext4 上不存在的路径 → `invalid environment block` 循环。

**约束**（手册 §15.2）：plain disk（无 LVM/RAID）、非校验和文件系统（无 ZFS）、
BIOS 或 EFI 固件（无 ATA/USB/IEEE1275）。FAT32+GPT+EFI 满足。

**鸡生蛋问题**（AnyBoot 方案的关键）：`load_env` 读的第一个文件仍是 `$prefix/grubenv`，
`env_block` 必须先被读到才会生效 → 若 `$prefix` 在 ext4 上，直接写 ESP 文件不会被读。
解法：在 `$prefix/grubenv`（若 prefix 落在 ESP 上）或 `$prefix/custom.cfg` 里 bootstrap。

## 「invalid environment block」根因与修复（20:16）
- 现象：装完 09_anyboot 后 GRUB 报 `error: invalid environment block`。
- 根因：**GRUB 的环境块是「预分配 1024 字节」的文件，GRUB 自己不会创建它**；
  而 `H:\EFI\arch-efi\grubenv` **根本不存在** → 09_anyboot 里的
  `save_env -f "${anyboot_env}" next_entry|saved_entry` 写向不存在的文件即报此错。
  （官方手册 §15.2 原文：The environment block is a **preallocated 1024-byte file**。）
- 修复：按规范字节级造块 —— `b"# GRUB Environment Block\n"`（25 字节，含 \n）
  + `#` × 999 补足到 1024，写到 `H:\EFI\arch-efi\grubenv`。
  已复核：size=1024、仅 1 个 LF、头 25 字节为 `# GRUB Environment Block$`、尾部全 `#`。
- 等价命令（Linux 侧）：`grub-editenv <ESP>/EFI/arch-efi/grubenv create`
  （注意：grub-editenv 只会「校验/创建」，不能把已有的坏块修好 —— 必须先 `rm` 再 create）。
- 关键认知：**环境块文件必须由外部预创建**；AnyBoot 在 Windows/macOS 侧写 `next_entry`
  时也走这条路（纯 1024 字节文本，原子替换 + 回读校验）。
- 搜索佐证：Fedora 44 同款报错源自「符号链接指向不存在文件」；Ubuntu 同款来自
  「手动编辑导致 grubenv 尺寸 ≠ 1024」。共同点都是**尺寸/存在性**问题，而非内容问题。
- 修复后用户确认「可以了」。

## 第五轮：ESP 目录识别（FAT32 + fs-uuid）、挂载勾选、打开文件管理器 + 两处界面调整

用户要求：①三端都能「打开文件管理器」看勾选挂载的 ESP 目录，并**自己判断是不是 FAT32、
提取其中的 uuid**；②主窗口「下次启动」文字重复；③电源操作按钮移到系统列表上方。

### 新增（backend）
- `EspInfo`（`path/root/device/fstype/fat/fat32/uuid/mounted/ownedMount/note`）+ 三端 `esp_probe`：
  - Windows：`windows_volume(letter)`（`GetVolumeInformationW`，extren 提到模块级，`grub_esp_dir`
    共用）→ 卷序列号即 fs-uuid。**实测**：H: FAT32/E537-7F31、S: ADDC-5447、R: A5EB-573A、
    U: 4F56-5256、C:/D:/Z: NTFS → `fat=false` 被拒。子路径 `H:\EFI\arch-efi` 归一化成 `H:\`。
  - Linux：`findmnt --json --output SOURCE,FSTYPE,UUID --target <path>`（`--target` 取包含该路径的
    那次挂载，所以填分区里任意路径都对）。能读 `/dev/sdX1` 引导扇区时用纯函数
    `fat_boot_sector()` 自己算簇数分 FAT12/16/32 并读 BS_VolID（blkid 的 `vfat` 分不出 16/32）；
    读不到（普通用户无权限）就退回 findmnt 的 fstype/uuid，如实写进 note。
  - macOS：`diskutil info`（+ `diskutil info -all` 分段解析，段间是整行星号）。Volume UUID 只有
    是 8 位十六进制才当 fs-uuid 用，否则 `uuid=None` 并在 note 里写明原值让人手工核对。
    挂载走 `diskutil mount <Device Node>`；`ActiveMount::unmount` 也按平台分（macOS 用 diskutil unmount）。
- 新命令：`detect_esp(path)`（非 FAT 一律拒 —— 否则同步会把 `/EFI/grub.cfg` 写到数据分区上；
  成功则把**分区根目录**存进 `grub_efi_dir` 并把 fs-uuid 存进 `grub_efi_uuid`）、
  `set_grub_mount(enabled)`（勾上=按 fs-uuid 挂载并保持；取消=只卸自己挂的那份；
  失败会把勾退回去，不让界面骗人）、`open_grub_dir()`（三端共用 `open_directory_in_explorer`）。
- `Settings` 加 `grub_efi_dir` / `grub_keep_mounted`；`GrubView` 加 `dir/esp/keepMounted/mountSupported`。
- `grub_scan(settings, reusable)`：`reusable` 是上一次自己挂的具柄，`merge_mount()` 决定复用/卸载
  （**挂载点必须一致**才复用，其余一律卸掉，绝不留没人管得着的挂载）。
- `apply_grub_error` 以前会把整个 `GrubRuntime` 换成 default → 旧的 `mount` 直接丢（`ActiveMount`
  没有 Drop）= 挂载泄漏，现在先 `take()` 再按 `keep_mounted` 决定留还是卸。
- Linux 挂载点从 `temp_dir()/anyboot-grub-<pid>` 改成固定的 `$XDG_RUNTIME_DIR|/tmp` + `anyboot-esp`，
  这样「打开文件管理器」看到的路径每次一样、可以收藏。

### 新增（frontend）
- GRUB 区顶部加「ESP 目录」行（输入 + 识别 + 打开文件管理器）、「挂载 ESP」勾选行 + `#grub-part`
  分区信息行（FAT32 / fs-uuid / 设备 / 挂载状态 / 出处），`#grub-message` 就近显示操作回执。
- Windows 上挂载不归我们管 → 勾选框改为**反映真实可访问性**（勾上+禁用），标签也换成
  「ESP 可访问（Windows 由盘符决定，无需挂载）」，不摆「没勾=没挂载」的假象。

### 两处界面调整
- **电源操作**从「GRUB 区之后 / 变量目录之前」移到 `#next-boot` 与 `#systems` 之间（页面最上方），
  `.system-actions` 去掉 `margin-top`。

  紧挨着下面的大字又是同一句 → 现在按与托盘 `menu_status_line` 相同的规则去重：
  相同/为空时给 `#status` 加 `.hidden`（不占位），出错/额外信息才显示。`renderSystems` 改为
  返回 `activeName` 供去重使用。

### 验证

  三种 FAT 类型 + 拒绝垃圾/短扇区、`esp_info_serializes_the_keys_the_window_reads`、
  `grub_efi_dir_and_keep_mounted_round_trip`（含老配置缺字段走默认）、Windows 的
