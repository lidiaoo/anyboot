## Windows 侧 ext4 直读接通（grub「自动读取」通道）

`linux_grub::probe_raw` 在 Windows 原来是 `Err("…还在做…")` 占位，现在真实现了。

改动三处：
- `channels/partitions.rs`：新增 `LINUX_GPT`（`0fc63daf-8483-4772-8e79-3d69d8477de4`）+ `Partition::is_linux()`，
  复用现成分区表缓存（已带 `offset`）。
- `channels/ext4_raw.rs`：新增 `#[cfg(windows)] FileSource::open_physical(disk, base, writable)`，
  打开 `\\.\PhysicalDriveN`、`base` = 分区起始偏移。`FileSource{base}` 本来就支持偏移读
  （`read_at` 就是 `pread(base + offset)`），这里只是补一个构造函数。
- `channels/linux_grub.rs`：把 macOS 里那 90 行「逐分区解析」抽成
  `scan_ext4(&mut Ext4, &Ext4Candidate)` 两端共用；Windows `probe_raw` 遍历
  `partitions::all()` 的 Linux 分区、按 offset 打开、调同一个 scan；`write_env_block`
  补 Windows 版（`disk1p3` → 反查 offset → 整盘读写）；`parts_for_sim` 的 Windows 分支
  从「恒返回不支持」改成读 `linux_probe_cache`。

关键事实（下次别重复踩）：
- **`probe_raw` 在 Windows 天生就在提权进程里跑**：`probe()` 非 Linux 一律走
  `probe_via_elevated`，物理磁盘 `CreateFile` 本来也要管理员，所以这里不用自己判断权限。
- 偏移来自 `Get-Partition` 的 `Offset`，**不需要 `DeviceIoControl`**（原方案里这句是多余的）。
- `PartReport.dev` 既有约定是 `disk{d}p{p}`（macOS `disk0s9` / Linux `sdb1`）。写路径靠
  `parse_win_dev` 反解，**认不出就报错，绝不猜偏移**。
- 写时**不复用**父进程的分区表缓存，重新查一次：写错偏移会写坏别人的分区。
- 自动扫描（`allow_fallback=false`）在 Windows 不弹 UAC，所以模拟扫描拿不到 Linux 内核清单，
  要用户点一次「重新读取」；提示语已改成这个意思，不再是「这一端不支持」。
- **未验证（到期更正）**：上一轮记「开发机没有 ext4 分区」是旧状态 —— 现在本机有
  **10 块** `0fc63daf` 分区（见下一节实测数据）。但 `\\.\PhysicalDrive0` 非管理员
  一律 `PermissionError`，所以真机路径仍要靠点「重新读取」弹 UAC 才能跑。

## 「没定位到你选的 ESP 对应的 Linux 分区」的根因（同日）

症状：Windows 上点「重新读取」能扫出 ext4 分区，但候选列表里一块都不中，落在
「没定位到你选的 ESP 对应的 Linux 分区：从下面的列表里选一块」。

根因：Windows 版 `probe_raw` 构造 ESP 身份时把 `fs_uuid`/`label` 留成了 `None`，只填了
`part_uuid`。而 `locate()` 认「哪块 Linux 分区挂的是这个 ESP」靠的是 fstab 里
`UUID=E537-7F31 /boot/efi vfat` —— **那个 UUID 是 FAT 卷序列，不是分区 GUID**。
没有它就永远只能按 PARTUUID 匹配（fstab 里几乎不这么写），于是 exact 恒不中。

修法（对齐 macOS）：
- 读 ESP 首扇区拿身份：Windows 走 `FileSource::open_physical(disk, offset, false)`，
  macOS 走 `/dev/rdiskNsM`，读 512 字节后**共用** `esp::fat_boot_sector`。
- **别自己固定读 0x43**：FAT12/16 的序列号在 `0x27`、卷标在 `0x2B`，FAT32 才是
  `0x43`/`0x47`。簇数判类型（<4085 FAT12 / <65525 FAT16 / 否则 FAT32）这件事
  `esp::fat_boot_sector` 已经做好了，`fat_volume_serial` / `fat_volume_label` 都改成委托它。
- 卷标全空格必须返回 `None`：空串会被 `LABEL=` 当成命中，等于随机选一块。
- 枚举口径也放宽到与 macOS 一致：**不筛 GPT 类型**，Linux 类型优先、其余兜底，
  靠 `Ext4::open` 判定；非 Linux 类型打不开不刷问题列表（MSR/恢复分区没有文件系统）。
- 提示语分三档，别再含糊成一句：`没扫到任何 ext4` / `还没认出 ESP` /
  `认出了 ESP 但读不到卷序列与卷标` / `认出了也有钥匙但 fstab 没挂它`。

本机实测数据（开发机，别当通用假设）：10 块 `0fc63daf` Linux 分区；ESP = `H:`，
GUID `b3fbe669-…`，但 **GPT 类型被写成 `ebd0a0a2`（微软基本数据）**，所以
`win_esp::list()` 永远是空表 —— 自动读取不依赖它（按 GUID 认），OC 通道才靠盘符兜底。
`Get-Volume` 和 `fsutil` 在这里都拿不到卷序列（前者 SerialNumber 为 null，后者要管理员），
卷标是 `ARCH-EFI`。

## Windows 免 UAC 提权：常驻特权服务（AnyBootHelper）

动机：UAC 是**会话级**的，对话框弹在主机交互桌面上。走 HTTP hub（手机）或无人登录时
永远点不到，`ShellExecuteExW(runas)` 连桌面都没有直接失败。所以「装一次、之后免提权」
不是优化，是远程链路的**前提**。

架构（`src-tauri/src/service_win.rs`，LocalSystem + 命名管道）：
- `elevate::run_privileged_op(op, args, fallback_args, out)` 是**唯一收口**：
  先走服务 → 服务不可用才回退 UAC。三种结果不能合并：服务做完/服务明确失败（不要再弹
  UAC 重报同一错误）/不可用（回退）。
- 服务回的是**与 `--out` 文件逐字节一致的那段 JSON 文本**（应答 `{"ok":true,"body":"<字符串>"}`），
  客户端原样落盘 → 下游解析器完全不知道这次走的哪条路。为此把五个 `*_main` 拆成
  `*_json()` + `channels::write_result_file()`（原子 tmp+rename，原四份重复实现合并）。
- op 白名单 5 个：apfs_scan / nvram_dump / oc_set_default / linux_grub_probe / linux_grub_write。
- 管道 DACL `D:(A;;GA;;;SY)(A;;GA;;;BA)(A;;GRGW;;;AU)` + `PIPE_REJECT_REMOTE_CLIENTS`；
  另校验**调用方映像路径必须等于服务自己的 exe**（GetNamedPipeClientProcessId +
  QueryFullProcessImageNameW）—— 别的程序连管道会被拒，且拒绝原因能回给客户端
  （所以 handle_client 必须**先收请求再认人**，反过来客户端只会收到 EPIPE 109）。

安全硬前提（这条不满足就整套别上）：**exe 必须在管理员独占可写目录**。
`install()` 直接拒绝 `%LOCALAPPDATA%`/用户目录/Temp/Downloads/Desktop 下的路径 ——
SYSTEM 服务指向用户可改写的 exe = 免费本地提权后门。因此 NSIS 改成
`installMode=perMachine`（装 Program Files），`--install-service` 幂等（已存在则停→删→建，
换目录后必须重建，否则服务里留着旧绝对路径）。

安装/卸载：Windows 服务注册与安装包**无关联**，卸载器默认不管。
`src-tauri/windows/installer-hooks.nsh`：POSTINSTALL → `--install-service`，
PREUNINSTALL → `--uninstall-service`（内部先停再删：服务运行时 exe 被锁，先删文件会卸载失败）。
升级时 Tauri 先跑旧卸载器（删服务）再装新文件（重注册）。MSI 不经过钩子，需手工跑一次。

踩到的 windows-sys 0.59 特性门（编译期才发现）：
`ReadFile/WriteFile/ConnectNamedPipe` 在 `Win32_System_IO` 后面（不是 FileSystem/Pipes 直接可见）；
`SC_ACTION_TYPE` 是 **i32**（`SC_ACTION_RESTART` 必须是 i32）、`SC_STATUS_TYPE` 也是 i32，
而 `SERVICE_STATUS.dwCurrentState` / `ENUM_SERVICE_TYPE` 是 u32 —— 混着用就是 E0308。

未做：设置页里「安装/修复/卸载助手」按钮；MSI 的 WiX ServiceInstall 片段。
文档：`docs/windows-免UAC提权-服务方案.md`。

## 19:50 Linux 免密提权方案咨询（未落代码，用户只要评估）
需求：Linux 端也要「免密提权 + 输入框密码兜底」。
候选方案（编号沿用对话）：A1 helper+polkit 规则 / A2 sudoers NOPASSWD / A3 root 常驻+Unix socket broker / A4 setuid 或 file caps / B5 udev uaccess 授设备权限 / B6 复用 udisks2 挂载。
- 现状事实：Linux 端**没有任何常驻特权组件**，提权全是 `elevate::run_elevated`、`grub_esp::stage_and_install` 用 pkexec 一次性拉起 → 卸载残留天然为零；macOS 才有 `helper_install`（launchd + 文件信箱）。
- 本机无 polkit（`pkaction` 不存在）→ 只靠 A1 不行，必须备 A2 或 A3 兜底。
- A3 结论：systemd 系发行版全覆盖（Debian/Ubuntu 系、Fedora/RHEL 系、Arch 系、openSUSE、deepin/UOS/麒麟），Alpine/Devuan/Artix/Slackware/MX 默认 sysvinit 不可用；容器/WSL2 需开 systemd。**卸载残留四件套**（priv 二进制、socket unit、service unit、系统组）+ 顺序陷阱：必须先停 socket 再停 service，否则 socket 会重新拉起；主程序删了 socket 还在 = 静默失败。组权限模型要求 `groupadd` + `usermod -aG`，且**新组要重新登录才生效**。
- 倾向：为「卸载干净」优先 A1(纯文件) + A2(纯文件)，拒绝 A3/A4；真要 A3 就随 deb/rpm postinst 装、AppImage 只能首次 pkexec 装一次并在 App 内提供「移除特权组件」。

## 21:05 给免密助手收边界（提交 73f3675 + 757513e）
装了 sudoers 之后风险面变了：**本用户下任何进程都能以 root 跑 `anyboot-priv`**，所以能读写哪里必须由程序自己把关。原先助手侧只判了「是不是 root 在跑」，等于没判。
- `grub_esp::guard_install_paths`（纯函数，好测）：目标拒写 `/etc /usr /bin /sbin /lib* /opt /root /proc /sys /dev /var /home /srv`；源拒读 `/etc/{shadow,gshadow,sudoers,ssh}`、`/root`、私钥；再要求绝对路径、无 `..`、源≠目标、两端都不是符号链接。`/var` 是**整棵**拒的 —— `/var/spool/cron/crontabs/root` 写一坨就是定时 root 后门；`/boot`、`/mnt`、`/media`、`/run/media` 下的 ESP 照旧放行。真正落盘再叠 `O_NOFOLLOW` + `0644` + 保留 mtime（上游靠 size+mtime 判「已同步」，丢了每次扫描都重写）。
- `linux_priv::guard_result_path`：`--out` 是 root 侧唯一「按调用方给的路径写」的入口。必须**直接**落在 `/tmp`、无 `..`、本身非符号链接（文件名含 pid、可预测 → 能抢注符号链接）。`write_result_file` 的临时文件改 `create_new + O_NOFOLLOW`。
- `verify_sudoers`：先按 `/usr/sbin /sbin /usr/bin /bin` 找 visudo，找不到才退回 PATH；执行时 `env_clear` + 固定 PATH —— root 吃调用方 `LD_PRELOAD` 等于「校验」变「跑我的程序」。
- 坑：`path.starts_with("/tmp")` 是**组件比较**，`/tmp/../etc/x` 能过（`..` 只是普通组件），所以 `..` 必须单独拒；反过来 `/tmpfoo` 天然不会误判。
- 验证：`cargo test --lib` 491 passed / 17 ignored（guard_tests 5 + linux_priv 6，含 `/tmp/../etc` 绕过、预置符号链接、`/var/spool/cron` 写入、`/mnt` `/media` 放行）；`cargo check --bin anyboot` Finished。
- 经验：这类白名单**放行用例和拒绝用例一样重要** —— 误伤的表现不是「越权被拒」而是「写 ESP 突然报错」，只测拒绝会漏。

## 21:40 澄清：那「两道闸」属于哪一端的逻辑（用户追问）

## 21:44 三端 ESP 定位对比（结论：这是三端共用的同一个 bug，不是 Linux 专属）
`resolve_esp_root()` **没有 cfg**，三端跑的是同一份逻辑；差异只在 `candidate_roots()`：
- **macOS**：`fs::read_dir("/Volumes")` 全量（mod.rs:387-396）。但 macOS 的 ESP 默认不挂载 → `/Volumes` 里通常根本没这块盘；`esp_mount()`（esp.rs:441）**只在 GRUB 链路被调用**（grub_esp.rs:934），**通道检测链从不调** → 这就是 macOS 单 ESP 机器看不出来的原因。
- **Windows**：`win_esp::list()` 按 GPT 类型 GUID 枚举（比另两端强，不需要挂载），但 `filter_map(|p| p.root())`（mod.rs:402-405）**只要带盘符的**（win_esp.rs:46）→ 没盘符的不进候选；`offline_extras` 里给「分配盘符」按钮（`SwitchSpec::MountEsp`）是三端**唯一**能一键修好前置条件的出口。
- **Linux**：4 固定路径 + `/proc/self/mounts` 已挂 FAT。**唯一**会「自动填好 `grub.efi_dir`」的端（grub_esp.rs:1113 回填 settings → linux_grub 解析进 runtime，即 `state.grub.efi_dir`）→ 提前 return 天天触发；未挂载分区既不存在于候选、也没有按钮。
**关键：`has_grub_signature` 认 `EFI/BOOT/BOOTX64.EFI`（mod.rs:247），而 Windows ESP 和 macOS 黑苹果 ESP 上必然有它** → 双 ESP 机器上「先枚举到的那块（系统盘）带任一签名就赢」同样会让 OC 落空。所以修法必须改公共 `resolve_esp_root`（返回候选集 + 每通道各自挑），**别只打 Linux 的 cfg 补丁**。
