### 第四十五轮·新发现（不在用户原始诉求内）：Android「生成密钥对」默认的 Ed25519 必然失败
**现象**：密钥页 →「在本机生成密钥对」→ 默认选 Ed25519 → 点「生成」→ toast
`生成失败：java.lang.NoClassDefFoundError: Faile…`（后面被 toast 宽度截断），密钥列表始终是空的，且
**logcat 里什么都没有**（catch 只 toast 不落日志 —— 与 KeyVault 同类毛病，值得后来人注意）。

**根因（已查实，非猜测）**：`com.github.mwiede:jsch:0.2.20` 是 **Multi-Release JAR**：
- `META-INF/versions/15/com/jcraft/jsch/jce/SignatureEd25519.class` ← Java 15+ 走 JDK 原生 EdDSA
- `com/jcraft/jsch/bc/SignatureEd25519.class` ← **Java <15 走 Bouncy Castle**

**Android 不认 MR-JAR 的 `META-INF/versions/`**（D8 直接忽略）→ 只能走 `bc.*` 那条路
→ 需要 `org/bouncycastle/crypto/params/Ed25519PrivateKeyParameters` 等（jar 内引用 42 个 BC 类）
→ 而 app 只依赖 jsch，没引 bcprov → `NoClassDefFoundError: Failed resolution of: Lorg/bouncycastle/…`
（官方 README 明确写着：用 ssh-ed25519/ed448 需 ≥Java 15 **或**加 `bcprov-jdk18on`。）

**影响面**：不只是"生成"。ed25519 的**签名**同样走 `bc.SignatureEd25519`
→ **导入的 ed25519 私钥连服务器时大概率也失败**（未实测，属推断）。Ed25519 恰恰是那个对话框的默认项。

**修复代价（决定要不要修的关键）**：`bcprov-jdk18on:1.77` jar = **8.37 MB**；
本项目 `isMinifyEnabled` **debug/release 都是 false** → 不会被 R8 裁掉
→ APK 从 **9.6 MB 涨到约 17 MB**。本地 Gradle 缓存里**已有** `bcprov-jdk18on:1.77`，可离线构建。
→ 因为体积翻倍属产品决策（且用户对改动面敏感），**已列选项交用户定夺，未擅自改**。

### 第四十五轮·Ed25519 结论：**不能修**（BC 与 jsch 升版都会打挂老装机）
顺着上一条查到底，结论是「维持现状 + 把原因写死」，**净代码改动只有注释、一个前置拦截、一行日志**。

**三个被实测否掉的方案**（都在 emulator-5554 + 跳板机 81.68.251.231:8022 上跑过）：
| 方案 | 结果 |
|---|---|
| 现状（jsch 0.2.20，无 BC） | 连接正常（隧道通、远端页加载）；Ed25519 生成失败：`NoClassDefFoundError` |
| 只加 `bcprov-jdk18on:1.77` | 生成仍失败；**连接被拒：`reject HostKey: [81.68.251.231]:8022`** ← 破坏性 |
| 加 BC + jsch 升 2.28.8（有 `writeOpenSSHv1PrivateKey`） | **Ed25519 生成真的成功了**（`ssh-ed25519 · SHA256:XerQN3FF…`，指纹、落盘都对）；但连接同样被拒 |

**根因（关键，别再踩）**：**只要 jsch 多做一套 EdDSA 实现（BC 到位，或升到 0.2.27+），主机密钥算法协商结果就会变**
→ 协商到的 host key 与老装机已存的那条指纹不同 → `TofuRepository.check` 返回 `NOT_INCLUDED`
→ jsch 去问 `userinfo.promptYesNo`，而本 app 的 UserInfo **故意不代答确认框**（指纹走 TofuRepository）
→ 硬拒绝，用户只能手动「重置信任」。
而本 app 的 TOFU 是**按服务器记一条指纹**、不按 key type 记 → **面向全部老装机的破坏性变更**。

**顺带查实的事实**：
- `KeyPairEdDSA.getPrivateKey/getBegin/getEnd` 在 jsch 里是**故意**抛 `UnsupportedOperationException` 的
  （源码注释：「writing VENDOR_OPENSSH_V1 isn't supported yet」；上游 issue mwiede/jsch#118 至今 open）。
  所以 **jsch 0.2.20 根本没法把 Ed25519 私钥落盘**，跟 BC 有没有无关。
- 0.2.27 起才有 `KeyPair.writeOpenSSHv1PrivateKey(OutputStream, byte[])`（唯一途径）。
- BC 的代价也不小：`bcprov-jdk18on:1.77` = 8.37MB jar，`isMinifyEnabled=false` 裁不掉，APK 9.3→16.3MB。
- `javap` 在这台机器上也会因 4G 地址空间崩（`Failed to reserve memory for metaspace`）→
  加 `_JAVA_OPTIONS="-Xmx320m -XX:MaxMetaspaceSize=128m"`；或干脆用 python 读 class 字节找方法名。

**最终处置**：不加 BC、不升 jsch；`build.gradle.kts` 里写长注释钉死这两条禁令；
`generateKey` 里对 Ed25519 前置拦截并给可读提示（老版本只显示「未知错误」）；catch 补 `tlog`（把堆栈写进 logcat）。
**要真正支持 Ed25519，前提是先改 TOFU**（按 key type 存指纹，或指纹变了要弹窗让用户重新确认）——那是另一个议题。

**构建链新坑（本机 4G 地址空间）**：给项目加 BC 后 Dexing 直接把 daemon 打崩：
`java.lang.OutOfMemoryError: Metaspace`（gradle.properties 里 `MaxMetaspaceSize=192m` 太小）。
解法：`_JAVA_OPTIONS="-Xmx768m -Xms64m -XX:MaxMetaspaceSize=512m"`（heap 仍压着，只放大 metaspace）。
**另外**：崩过一次之后的「成功」构建可能是增量残料，**APK 体积/内容都要按 clean 构建核**——
本次 clean 后 9.33MB，而崩溃后增量产物虚报到 12.7 / 16.3MB。

**收尾（本轮已落袋）**：
- 提交 `e2035cd`：`build.gradle.kts` 两条禁令长注释 + `generateKey` Ed25519 前置拦截 + catch 补 `tlog`；`MEMORY.md` 修好上次误删的冒号并补 Ed25519 结论（6205 → 3305 字符，回到注入不截断的范围，细节仍散在 `MEMORY-detail-*.md`）。

# 第四十七轮：传输「暂停 / 继续」（断点续传）

**用户原话**：「没有传输暂停和恢复下载的功能吗」—— 之前只有「取消」（清掉半截文件）和「重试」（从头来），确实没有暂停续传。本轮补上，**上传/下载都支持**。

**先查源码再动手**（这是本轮最值的一步，别靠记忆猜 API）：从 gradle 缓存的 `jsch-0.2.20-sources.jar` 解出 `ChannelSftp.java` 逐段读，jsch 自己就带续传：
- `get(src, dst, monitor, ChannelSftp.RESUME)`（**路径变体**，不是 OutputStream 变体）：先 `_stat` 远端拿总长、比本地 `length()`（**本地更大 → 抛 "failed to resume"；相等 → 直接 return**，等于「已经下完了」），再用 `new FileOutputStream(dst, true)` 追加、`_get(..., offset=本地长度)` 从断点 READ。
- `put(input, dst, monitor, RESUME)`：`_stat` 远端拿已传长度 → **`src.skip(已传)`**（跳不动就抛 "failed to resume"）→ `sendOPENA`（SSH_FXF_APPEND）→ 从 `offset=远端长度` 续写。
- 常量就在 `ChannelSftp`：`OVERWRITE=0 / RESUME=1 / APPEND=2`（0.2.20 就有，**不用升版**，升版会打挂老装机的 TOFU）。

**关键坑（差点写错的地方）**：两种方向的**断点进度上报方式不一样** ——
下载 RESUME 时 jsch 会在 `monitor.init()` 之后**补一次 `count(本地长度)`**（`ChannelSftp.get` 里的 `if (mode == RESUME) monitor.count(skip);`），上传 RESUME 时**不报**。
所以 `Progress` 做成两个参数：`initialTransferred`（上传续传时喂远端已传长度）+ `swallowFirstCount`（下载续传时把那一笔当**基线**吃掉）。
不特判的后果：`transferred` 一开始就跳到断点值，而 `baseline` 还是 0 → 速度瞬间虚报成几十 MB/s。
另外正常传完要 `settleAtTotal()`（RESUME 在「本地已跟远端一样大」时会一个 count 都不报，进度条会停在中间）。

**设计**：暂停 = 走跟取消同一条机制（进度回调返回 false，jsch 就地把循环 break，**不断共享会话**），差别只在收尾时**不清半截文件**。
- `Task` 里把 `cancelRequested` 换成 `stop`（`STOP_NONE/STOP_CANCEL/STOP_PAUSE`）+ `baseline`（算速度用）+ `resumed`。
- 新增 `STATE_PAUSED=4`、`STATE_SUPERSEDED=5`；`isPending()`（进行中/已暂停）区分「还能点按钮」与「已收尾」，`active()/finished()/clearFinished()/newestFinishedUpload()` 全部改按 pending 划分。
- `resume()` **新建一条任务**（跟 `retry` 一致，历史留着），把原暂停记录标成 `STATE_SUPERSEDED`「已接续（本次从 X 接着传）」—— 否则每点一次「继续」都会在清单里留一行没有意义的「已暂停」僵尸行。
- `pendingFor(direction, remotePath)`：**挡住重复发起**。两条任务写同一个文件（下载各自以覆盖方式打开本地、上传各自 APPEND 远端）会互相踩出坏文件，连点两下按钮就能撞上。下载/上传入口、`resume`、`retry` 都过这道闸。
- 取消一条**已暂停**的任务时没有传输线程会来收尾，得自己 `discardPartial()`：下载删本地；上传借 `liveSession()` 另开 sftp 通道删远端，会话已被回收就如实说「半截文件可能还在服务器上」。
- UI：running 显示「暂停/取消」，paused 显示「继续/取消」，superseded 无按钮；两态都画进度条，暂停时定格并标「已暂停 · X / Y · 速度」；续传的行在副标题后加「· 续传」。
- 已知边界（**没做**，要单独提）：任务表是进程内静态结构，**杀进程后暂停中的记录会丢**（半截文件还在但没人认领）。跨进程续传要先做任务持久化；「重进 App 再点同一个文件」目前是**重下**（`FileOutputStream` 截断），不会自动接上——刻意不自动接，因为远端换过文件时会拼出坏文件。

**本轮最大的坑：不是 dump 的锅，是 Compose 跳过重画。**
暂停后表头已经变成「进行中（0）· 已暂停（1）」，行里却还是「暂停 / 取消」和旧进度 —— **截图和 dump 都一致复现**，所以不是取样陈旧。
根因：`Task` 里全是普通可变字段（`volatile long/int`），Compose 看不见；`TransferRow` 是**独立 composable**、入参又是同一个 `Task` 实例 → Compose 判定「入参没变」**整行跳过**，行内读到的永远是最后一帧。
同一文件里 `SessionsPage` 之所以没这毛病，是因为它的行**内联**在页面函数体内（页面函数本身会重跑）。
**修**：`TransferRow(task, tick)` 把每次都变的 `transferTick` 一起传进去。
**教训（已回写 skill）**：上一轮把「进度数字卡住」判成「`uiautomator dump` 太密把 UI 饿死」是**误判**——当时是重进页面后才看到新数值，于是以为实时刷新是好的。判据应该看**表头与行是否一致**。

**顺带修正一个判据**：**别拿 APK 体积当「有没有变更」的依据**。本轮加了约 250 行代码，`classes3.dex` 768,476 → 777,644（压缩后 315,787 → 320,361，+4.5KB），但**整个 APK 的字节数一模一样**（9,361,632，md5 变了）—— 打包对齐/填充把这点差值吃掉了。核变更要解 dex 搜符号。

**交付**：clean 构建 `gradle clean :app:assembleDebug --offline` → 9,361,632 B，md5 **`efb999611e5197b74fc39e564be5405c`**，`mobile/AnyBoot-remote-v1.2-compose-debug.apk`（同源）。dex 核到 `点「继续」接着传` / `已接续（本次从 ` / `STATE_SUPERSEDED` / `pendingFor` / `已暂停 · ` 等新符号。

## 第四十七轮续（传输任务持久化 + 断点远端校验）

上一轮留了「杀进程后暂停记录会丢」，这轮把它补上：任务表落盘 + 续传前核对远端。

**持久化（`TransferManager.java`）**
- 存 `<filesDir>/transfers.json`（`org.json`，项目里已在用，不加依赖）。装回时机：`ServersActivity.onCreate` 里 `TransferManager.restore(this)`（`setContent` 之前）。
- 装回规则：`state==RUNNING` 的记录一律降级成 `STATE_PAUSED` + `interrupted=true`，文案「上次没传完（App 关掉了），点「继续」接着传」，并把 `transferred` 用**本地半截文件的实际长度**纠正（进度落盘有 3 秒节流，会偏小）。
- 写入用 `writeText`：写 `<name>.tmp` → `flush()` → `getFD().sync()` → `renameTo`。进度是半路落盘的，非原子的写会留下半个 JSON。
- `persist()` 挂在 `register/finish/clearFinished`；`persistProgress()` 挂在 `Progress.count()`，**3 秒节流**。
- **`startDownload` 必须提前把 `localPath` 算出来**（`defaultTarget`）。原先只在 `runDownload` 里算，于是「进程被杀在 RUNNING 状态」的记录 `localPath` 是空的 → 装回时找不到半截文件、只能显示「已传 0 B」、`total` 也是 -1。
- 上传源跨进程要能读：`OpenDocument` 的结果 `takePersistableUriPermission(uri, FLAG_GRANT_READ_URI_PERMISSION)`（拿不到只记日志、不拦本次上传）。

**续传前核对远端（这轮的真正价值）**
- 下载：起手记 `remoteSize + remoteMTime`；续传前 `lstat` 重取，**任一不同**就删半截文件改为重下，结论文案「（服务器上的文件变过，已改为重新下载）」。没有这道闸，追加只会拼出一个**看着完整、内容错位**的文件——长度对、md5 全错，比报错难查得多。
- 上传：暂停时记 `remoteSize = transferred`（= 远端当时的大小）；续传前若远端 `> remoteSize`（有人往同一个文件写过）改为重传，文案「（服务器上的文件比预期大，已改为重新上传）」。
- 兜底：半截文件比远端还长也作废重下（远端 size/mtime 没拿到时走这条）。

**⚠️ 测试抓到的真 bug：`resume()` 漏拷两个字段，整道校验成了死代码。**
`resume()` 新建任务时把 `serverId/name/remoteDir/remotePath/localPath/sourceUri/total/transferred/baseline` 都带走了，**唯独漏了 `remoteSize` / `remoteMTime`** → 新任务里是 `-1` → `task.remoteSize > 0 && task.remoteMTime > 0` 恒假 → 校验永远不跑。
实机证据（设备上 `run-as com.anyboot.remote cat files/transfers.json`）：正在续传的那条记录 `"remoteSize":-1,"remoteMTime":-1`，而它**真的就在已经变过的远端文件上接着往后追加**（远端 16 MiB→17.8 MiB，它从 479 KB 一路 APPEND 到 16.3 MB），进度条还一路涨到「17.0 MB / 17.0 MB」——典型的静默产坏文件。
**修**：`resume()` 里补 `task.remoteSize = previous.remoteSize; task.remoteMTime = previous.remoteMTime;`；并让校验命中后把基线**刷新到新文件**（否则这次重下再被暂停、再继续时会拿旧值比一遍、又白白从头下一遍）。
**教训**：这种「新增字段 + 复制式构造函数」的组合必查一遍——新增 `Task` 字段时要把所有 `task.x = previous.x` 的地方过一遍，编译不会提醒。

## 本地 SFTP 靶机（`~/.cache/ab-droid/ab_sftp_fixture.py`）

原来的靶机是用户那台公网跳板机，被我这轮自己搞没了（见下「事故」），于是自建一个不依赖外部服务的：**paramiko 手写 SSH + SFTP 服务端**，跑在 `127.0.0.1:2323`，模拟器经 `adb reverse tcp:2323 tcp:2323` 访问。密码 `abtest/abtest123`，root = `~/.cache/ab-droid/sftp-root`。
- 为什么不用真 `sshd`：沙箱 `/etc` 只读，`useradd` / `chpasswd` 全失败（`Authentication token lock busy`），密码认证起不来。paramiko 在用户态跑、认证自己说了算。
- paramiko 的 `SFTPServerInterface` **只是骨架**（全部 `SFTP_OP_UNSUPPORTED`），得自己实现本地盘读写：`open` 里按 flags 映射成 `"ab"/"wb"/"a+b"/"r+b"/"rb"` —— **`SSH_FXF_APPEND` 必须映射成 `"ab"`**，这正是 jsch `RESUME` 上传要的语义（`seek()` 被忽略、永远追加）。下载续传靠 `open`+指定 offset 读，天然支持。
- **线程要陪着客户端，不能「20 秒没会话通道就断开」**：应用连上后可能先握手、隔一会儿才开 SFTP，提前断开会让它记一次「连接失败」进入自动退避，后面全被 `连接失败过，N 秒后再试` 挡住（这个坑浪费了一轮排查）。
- `--rate KB/s` 限速（`Handle.read/write` 里 sleep）：本地 SFTP 8 MiB 一眨眼就完，不限速根本来不及按「暂停」。
- **坑：沙箱把 `unlink` 钩给了 safe-delete**（改成「移入回收站」），而进程 `HOME=/root` 时回收站不可写 → 失败关闭，`os.remove` 抛 `OSError` 且 **`errno=None`** → paramiko `convert_errno` 映射成 `SFTP_FAILURE`，客户端只看到 `Failure`。**跑任何要删文件的靶机/服务，先给 `HOME` 指到可写路径**。
- 自测脚本要点：offset 读、`"ab"` 追加（故意 `seek(0)` 验证被忽略）、`remove`。

**补记（同日晚，收进 skill `android-sftp-fixture` 时又踩到的一个阴坑）**：把「保活循环」写成
`while transport.is_active(): transport.accept(1.0)` —— **`accept()` 返回的通道拿到就丢，会被 GC 顺手关掉**。
客户端请求 SFTP 子系统时直接吃 `paramiko.ssh_exception.SSHException: Channel closed`，
而服务端日志一切正常（握手完成、认证通过）后面跟一行「断开」，很难往 GC 上想。
修：把 accept 回来的通道存进 list 保引用（SFTP 子系统处理器本来就是独立线程跑的，`accept()` 并非必需，
要调就得接住返回值）。顺带把 `--rate`、`SFTPServerInterface` 得自己实现本地盘读写、
`SSH_FXF_APPEND → "ab"` 这些一起固化成了 skill。
