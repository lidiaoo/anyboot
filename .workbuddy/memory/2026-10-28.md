# 2026-10-28

## OC 扫描性能：分段埋点（a076ae1）

用户诉求：「先把这些操作记录日志、埋点、算各个步骤耗时、最后算出来」，并质疑「默认进 anyboot 为什么不提权扫一遍」。

### 做了什么
- 新增 `src-tauri/src/perf.rs`：`begin()` / `span(name)` RAII / `flush(app, total_ms)`。
  - 表**按 thread_local 隔离**。教训：第一版用全局 `Mutex`，启动线程 `thread::spawn(refresh_and_update)` 与前端触发的刷新会**并发**跑两轮，`begin()` 互相清表 → 日志缺段（`channels.all x1` 却有 `esp.resolve x2`）。改成 thread_local 后两份日志完全自洽。
  - `trace_enabled` 为假时整表丢弃，埋点不产生格式化开销。
  - 口径：span **含子**，各行相加 > 总耗时，是刻意的。
- 埋点点位：`vars.scan` / `grub.refresh` / `channels.refresh` / `channels.{sdboot,opencore,clover}` / `esp.{resolve,candidates,probe,drive_letters,offline_extras}` / `oc.{preview,volumes,nvram_order,preboot}` / `apfs.scan` / `cmd.{get_partition,partition_guids,get_partition_apfs,lsblk_*}`。
- 输出形如 `trace.log` 里 `[perf]` 连续多行，按耗时降序 + 占比 + 调用次数。

### 实测（Windows 11，含 macOS+双 ESP，debugTrace 开）
单轮总耗时 **8.3~8.5s**，三段完全自洽：`channels.refresh 6181 + grub.refresh 2138 + vars.scan 2 ≈ 8321`。

| 段 | 耗时 | 次数 |
|---|---|---|
| channels.all | 6181ms (74%) | 1 |
| ├ esp.resolve | 2370ms | 1 |
| │ ├ esp.candidates | 1210ms | 1 |
| │ └ esp.probe | 1158ms | 1 |
| └ oc.preview | 3810ms (45%) | 1 |
| 　 ├ oc.volumes | 965ms | 1 |
| 　 ├ oc.preboot | 953ms | 1 |
| 　 └ （未细分的组装/遍历） | ~1890ms | — |
| grub.refresh | 2138ms (25%) | 1 |
| **cmd.get_partition** | **4045ms** | **x4** |
| **cmd.partition_guids** | **3295ms** | **x3** |

→ **7 次外部命令冷启动 ≈ 7.3s，占总耗时 88%**。单次 1.0~1.1s。上一轮「估算 4.4s、3~5 次」偏低，实际调用次数是 7 次。

### 默认不提权的原因（本轮结论，待用户拍板）
`lib.rs` setup 末尾 `thread::spawn(|| refresh_and_update(&app))` 全程非提权。非提权拿不到两类东西：
1. 固件变量 `Boot*` / `OCBt*`（**读也报 1314/5**）→ 默认项标不出来、启动顺序空；
2. 原始磁盘读（`\\.\PhysicalDriveN`）→ APFS Preboot 扫不到，macOS 条目缺失。

现状是「先非提权扫（快、不打扰），缺的部分给 ⤴ 按钮手动补」，代价是**每次启动要手点两次提权**（APFS 扫描一次、启动顺序再一次 = 两次 UAC）。可选方案：A 合并成一个 `--scan-privileged` 子命令 + 设置项「启动时自动提权」（一次 UAC 拿全）；B 注册 SYSTEM 计划任务，后续免 UAC 触发（安装时一次授权）；C 维持现状只改文案。
**用户 2026-10-28 决定：提权策略「先不动」，优化「一起做」。**

## 优化落地（6806b8e）：8.3s → 1.0s

细埋点补完后 1890ms 的归属查清了：**`oc.spec` 里每个 generic 条目都调
`oc_menu::volume_root(卷标)` → 整个 `volumes()` 重算 → 又一次全量分区查询**。
本机 2 个 generic 条目 = 1.87s。

- 新增 `channels/partitions.rs`：一次 `Get-Partition` 全量（DiskNumber/PartitionNumber/
  DriveLetter/Size/**Offset**/GptType/Guid）+ 60s 缓存；`is_esp`/`is_apfs` 比 GUID 前 8 位。
- **查询持锁做（single-flight）**：启动时 `thread::spawn(refresh_and_update)` 与前端
  刷新并发，先读缓存后查询的写法会让两轮各起一次进程（实测两轮各 1000ms）。
- `win_esp::list` / `esp::windows_partition_guids` / `apfs_reader::container_location`
  三处全部改读这张表；`win_esp::mount()` 成功后 `partitions::invalidate()`。
- `oc_default::entry_spec` 改收 `esp_label: Option<&str>`（调用方在 preview 里算一次）。
- 真机诊断测试 `channels::partitions::tests::real_partition_table`（`#[ignore]`）：
  `cargo test --release --lib real_partition_table -- --ignored --nocapture`。

### 实测对比
| 指标 | 前 | 后 |
|---|---|---|
| 冷启动单轮 | 8328ms | 1007ms（-88%）|
| 同进程热刷新 | 无（每次都重跑）| **25ms** |

### 真机事实（重要，别当 bug 修）
**本机 ESP 的 GPT 类型是 `{ebd0a0a2-b9e5-4433-87c0-68b6b72699c7}`（微软基本数据分区），
不是 c12a7328** —— 所以 `win_esp::list()` 在这台机器上**一直返回空表**，`candidate_roots`
走的是 26 盘符兜底（日志里 `esp.drive_letters` 每次都有值）。别据此判断「ESP 枚举坏了」。

`apfs.scan` 常年 0ms 也是正常的：非提权进程开 `\\.\PhysicalDrive0` 立刻 PermissionDenied，
预演里会补一条 info 让用户点「提权重扫」——不是「没扫」。

## 「设为默认要两次才回显」根因（时序反了）

`privileged_set_default_main` 里 **`dump_boot_vars()` 写在 `set_default()` 之前** ——
回传给父进程的是**写入前**的 `OCBtOrder`，父进程 `store_snapshots_from_vars` 存成
快照（TTL 30 分钟），随后 `refresh_channels` 按旧表算默认项 → 点了没变化；
第二次点击带回的「旧表」恰等于第一次写完的状态 → 「要两次才回显」。
**修法：先写后 dump**（失败路径照样 dump，只是顺序挪到操作之后）。

排查心法：凡是「提权子进程回传数据 → 父进程存缓存 → 立刻刷新」的链路，
**必须确认回传数据是操作之后采的**；写进缓存的旧值会伪装成「界面不刷新」的 bug，
而且表现得极像前端问题（第二次就对了 = 典型的「缓存里是上一次的值」）。
