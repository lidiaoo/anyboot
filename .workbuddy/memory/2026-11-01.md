### release job 第一次挂：merge-multiple 保留子目录
- 现象：`ls: cannot access 'artifacts/*setup*.exe'` → `cp: cannot stat ''` → exit 1，release 没建出来（构建全成功，纯工作流 bug）。
- 根因：`actions/download-artifact@v4` 的 `merge-multiple` 按**产物 zip 内部相对路径**落地。desktop-macos 只匹配 `dmg/*.dmg` 一个目录 → 文件落在 `artifacts/` 根；desktop-windows 同时匹配 `nsis/` 与 `msi/` → LCA 是 `bundle/`，解出来是 `artifacts/nsis/*.exe`、`artifacts/msi/*.msi`。
- 修法（fe4d584）：命名步骤全部改用 `find artifacts -type f -iname <pattern>` 递归取第一个，找不到就打印 artifacts 实际内容再退 1。本地用模拟目录结构（nsis/msi/deb/rpm/appimage 子目录 + 根目录 dmg/apk/ipa）验证通过。
- 重跑方式：**tag 必须重指**——`gh run rerun` 用的是该 run 自身 SHA 的工作流文件，改 main 不生效。做法：`git tag -d v0.2.1` → 在新提交上重打 → `git push origin v0.2.1 --force`（此时还没有 release，无副作用）。

## 安卓更新「下载失败」核查（用户报障）

用户手机报：`直连：SHA-256 不匹配；ghfast：connection closed；ghproxy：SHA-256 不匹配（已尝试3个源）`。

核查结论 —— **包和校验值都是对的，问题在链路**：
- 下载 `AnyBoot_0.2.1_debug.apk` 实算 `1725376d…66a3c`，与 release 的 `SHA256SUMS.txt` 逐字相同；
  用 AppUpdate.kt 的 `sha256()` 同款代码在 JVM 复算，64 位、同值（所以不是 `"%02x".format(Byte)`
  的符号问题，Java Formatter 对 Byte 走无符号）。
- 直连与 ghproxy 的响应头都是 `content-length: 12915949` + TLS 正常 ⇒ 手机拿到的是
  「长度自洽但不是这个包」的响应（被代理改写 / 返回拦截页），不是半截包（半截会被 OkHttp 抛
  unexpected end of stream）。
- 用户手机上那版 APK 是 versionName=0.2.0 的 main 开发构建（v0.2.0 tag 里根本没有 AppUpdate.kt，
  更新功能是 24758fa 才进来的），报错文案与当前代码逐字一致，可确认同源。

镜像实测（2026-11-01，本机逐个下完整包比 SHA-256）：
- 可用：`gh-proxy.com`（唯一，字节完全一致）
- 不可用：ghfast.top（TLS 直接断 unexpected eof）、ghproxy.net、ghproxy.cc、ghproxy.cfd、ghp.ci、
  hub.gitmirror.com、github.moeyy.xyz、gh.llkk.cc、gitproxy.click、gh.ddlc.top、kkgithub.com、
  cdn.jsdelivr.net

改动（commit de8edba）：长度自检 + text/html 识别 + 哈希不匹配时带实收大小与双哈希前 8 位 +
每源重试一次 + MIRRORS 改成 ghproxy→ghfast + 错误态加「用浏览器打开下载页」。

应急绕过：包放 `/tmp/ab-share`，`python3 -m http.server 8899 --bind 192.168.0.120`，
手机同 Wi-Fi 打开 `http://192.168.0.120:8899/AnyBoot_0.2.1_hardened.apk` 直接装。
长期正解：**让手机从已连的桌面端拉包（局域网更新源）**——桌面端下载通道是通的，手机只走内网。
