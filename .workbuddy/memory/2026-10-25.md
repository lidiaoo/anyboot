## 内置 Tailscale 引擎（tsnet sidecar）覆盖 macOS/Linux —— 3b408a4

用户反馈：内置引擎只在 Windows 测过，mac/linux 报「内置 Tailscale 引擎缺失」。

**根因（两层）**：
1. `src-tauri/binaries/` 只有 Windows 的 `anyboot-tsnet.exe`，`tauri.conf.json` resources 也只打包它。
2. Rust `sidecar_candidates` 在非 Windows 找不带 `.exe` 的 `anyboot-tsnet` —— 旧 Linux deb 包里其实误打进过 `.exe`（`usr/lib/AnyBoot/binaries/`），但名字对不上照样找不到。

**修复**：
- sidecar 交叉编译 4 目标 `anyboot-tsnet-{linux,darwin}-{amd64,arm64}`（CGO_ENABLED=0 静态链接，go test 通过）。
- Rust：unix 文件名带 OS+arch；查找链补 `resource_dir()/binaries/`（mac=.app/Contents/Resources、linux=/usr/lib/<id>、win=exe 目录）；spawn 前 `ensure_executable` 补 0o755（打包链路丢执行位兜底）。
- 打包分平台：主 conf resources 移除，`tauri.{windows,macos,linux}.conf.json` 各自只打本平台文件（平台配置与主 conf 深合并）。

**Go 工具链（本机）**：`/home/jianghh/.workbuddy/binaries/go/go/bin/go`（go1.27.3 官方 tarball，阿里云镜像 mirrors.aliyun.com/golang）。本机 `/usr/bin/go` 是 gccgo 1.18，编不了 tailscale.com/tsnet。

**本机编译坑**：
- `/tmp` 是 10MB tmpfs → Go 编译器 $WORK 写不下（no space left on device），必须 `TMPDIR` 指到大盘（用了 /home/disk1 下目录，/home 有 57G）。

- **cargo check 在本仓库目录跑不了**：build-script 指纹扫描报「Could not read repository exclude / Permission denied」（.git/info/exclude 明明可读，chmod 666 也没用，strace 被 ptrace 禁止挡住，环境怪癖）。**绕法：rsync src-tauri+ui 到仓库外（如 /home/disk1/anyboot-check/）跑 cargo check**。注意必须连同级 `ui/` 一起拷（`include_str!` 引用 `../../ui/*`）。

## 09:5x 本机 arch 系统排障 + 系统 Tailscale Linux 层补齐（commit 11e7c61）
- **重大发现：沙箱就跑在这台 arch 主机上**（hostname=`arch`、tailscaled 二进制时间戳一致）。沙箱对 /etc、/usr 只读（/usr 是同分区额外 ro 挂载），systemd bus 够不着 → 系统级操作只能打包脚本让用户跑（如 /home/jianghh/fix-tailscaled.sh）。
- tailscaled 起不来根因：unit 指 /usr/sbin/tailscaled（upstream Debian 风格），本机 /usr/sbin 是真实目录且无该文件 → 203/EXEC + start-limit-hit。修复=systemd drop-in override 指向 /usr/bin/tailscaled。`/usr/sbin` 缺系统软链是更深的坑（filesystem 包布局被破坏），待查。
- **Funnel「Access denied: serve config denied」实为 tailscaled 本地权限闸门**（serve/funnel 只允许 root/operator），不是 tailnet 策略；sudo 一跑就过是铁证。一次性解法 `sudo tailscale set --operator=<user>`。tailnet nodeAttrs funnel 授权是另一道独立的门（较新 tailnet 默认放行）。
- 系统 Tailscale（hub_tailscale.rs）Linux 层补齐：service_running 走 systemctl is-active；启停走 systemctl（polkit 弹框）；up 失败与 funnel denied 的人话翻译。前端按 service_running>=0 亮副开关，零改动。

## macOS「Tailscale 直连」报错文本进地址（已修，commit bc5e757）

**现象**：UI 直连地址显示 `http://The Tailscale GUI failed to start: …(Tailscale.CLIError error 3.):12300`。

**根因（二分锁定，证据确凿）**：macOS App 版 CLI 用 `SHLVL`（只有 shell 会设）判断调用方是不是 shell。
Rust `Command::spawn` 的子进程没有 SHLVL → CLI 误判为 GUI 启动场景 → 试图拉起 Tailscale.app →
失败后 **exit 0 + stdout 全是报错文本**（GUI 起没起都一样，`env -i` 复现、GUI 运行中同样复现）。
`/usr/local/bin/tailscale` 只是 68 字节 shim 指回 App 版，候选兜底无效。
老 probe() 对 `ip -4` 输出只查非空 → 报错文本当 ip 采信置 running。

**修复**：
- `cli_command()`：macOS 下统一 `env("SHLVL","1")` 强制 CLI 分支（GUI 不在跑也正常；standalone 版不读它）。
- `run_cli_raw()`：run_cli/run_cli_full 合并，5s 超时 + stdout/stderr 并发读——CLI 在坏环境会**挂死不退出**
  （实测残留两条 status --json 僵进程，`output()` 无超时会把探测线程拖死；并发读防大 tailnet 撑爆管道）。
- `plausible_ipv4()`：probe 三个 ip 采信点全加严格形状校验（4 段 0-255），非 IP 文本一律不采信。
- 兜底：GUI 报错文本识别为 `needs_gui` 态，前端给「打开 Tailscale.app」按钮（`gateway_tailscale_launch_gui` = `open -a Tailscale`）。

**验证**：cargo test 290 全绿（新增 plausible_ipv4/gui_failed/first_line 3 组单测）；universal .app 重编装机；
shell 级实机验证 `env -i HOME=… SHLVL=1 <CLI> ip -4` → `100.118.110.36`（GUI 已退）。**push 由用户做**。

**取证手法**：`env -i` 复现报错；`env -i <单变量> <CLI> ip -4` 逐个/折半二分触发变量（写 /tmp/ts_bisect.sh
对全量 env 折半，最终收敛到 SHLVL）；卡死进程 `pgrep -fl Tailscale` 清理（kill 无害，网络扩展别动）。

- 20:40 单实例改成「接管式」：打开软件时自动结束上一个进程再启动（lib.rs，README 同步）：
  - 三道闸门（防误杀）：① `anyboot.lock` 抢不到 ② `anyboot.pid`（**单独文件**，LockFileEx 整段独占锁导致锁文件里读不到内容）里有 believable 的 pid ③ `is_same_app_process(pid)` = 比**可执行文件 basename**（AppImage 每次挂载路径不同，比全路径永远对不上）。任一不成立 → 退回老行为（提示「已经启动」后退出）。
  - 先礼后兵：unix SIGTERM → 等锁 30×100ms；3 秒不退 SIGKILL 并把接管前抓的子孙快照一起杀。**Tauri 没装 SIGTERM 处理器**，SIGTERM 是直接死（走不到 RunEvent::Exit），所以「先礼」成功后还要 `reap_orphaned_children`：只杀 ppid ∈ {0,1} 的（已成孤儿），避免 pid 被回收后误杀。Windows 直接 `taskkill /PID x /T /F`（/T 才带走 WebView2 子进程；关窗默认是隐藏到托盘，没有可用的优雅退出）。
  - 平台取值：Linux `/proc/pid/exe` + `/proc/pid/task/*/children` + `/proc/pid/stat` 解 ppid；macOS `ps -o ucomm=` / `pgrep -P` / `ps -o ppid=`；Windows `tasklist /FI PID eq`。`ANYBOOT_CONFIG_DIR` 不同 = 不同锁/pid → 多套验证模式不受影响（实测两实例共存、双端口 200）。
  - 测试：`core_tests` 新增 4 个（pid 文件乱码零容忍 / 等锁轮询 / 子孙枚举 / **接管全链路**——用 `current_exe()` 起一个同程序的 `#[ignore]` 假实例占锁，再真把它 SIGTERM 掉并拿到锁）。`cargo test --lib` 315 通过 3 ignored。
  - 真机 E2E（Xvfb + 真实二进制）：A=38 在跑，起 B=128 → `startup-debug.log` 记「检测到上一个实例 pid=38 → 先结束它再启动」「已退出 → 拿到单实例锁（补收 0 个残留子进程）」；A 死、B 活、pid 文件=128、HTTP 200。
  - **Xvfb 跑 GUI 的坑**（已补进 `linux-x11-window-repro` 技能）：`ulimit -v` 4GB 时 llvmpipe JIT abort（`LLVM ERROR: Unable to allocate section memory!`）→ 必须 `GDK_GL=disable WEBKIT_DISABLE_DMABUF_RENDERER=1 WEBKIT_DISABLE_COMPOSITING_MODE=1`；Xvfb 要 `-ac`；每个 Bash 调用各自一个 mount namespace，Xvfb/应用/断言必须同一次调用跑完。
